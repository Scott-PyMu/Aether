## 2. 新增/残留问题

### 2.1 P1（高风险）

| 编号 | 级别 | 类型 | 问题 | 依据 | 建议 |
|---|---|---|---|---|---|
| P1-1 | P1 | 设计/适配器 | 旧会话补选只在 IPC/D6 参数层定义，未定义三个适配器如何消费 `session.send.provider_id/model`：旧会话的原生会话是在无 provider（或 legacy 单供应商 env）下创建的；补选后 Claude 可按 per-run env 处理，但 Codex 的 per-session `CODEX_HOME/config.toml`、DSH 的 per-session profile 何时创建/切换、原生会话上下文是否保留、失败如何回滚均未写明。E2E 只写“旧会话补选正向”，不足以证明三运行时行为一致。 | ADR §2.1-4:79、§2.1-5:85-88、§5.1:198、§7-6:285；设计 D6:422、D7:487、D10:592；P1 计划 M7-10 DoD 6:371 | 在 ADR/设计补“旧会话补选适配器语义”：三运行时统一规则；Claude 直接 per-run env；Codex 在首次补选 send 时创建/切换到 per-session `CODEX_HOME` 并物化 config；DSH 同理 profile；明确原生会话上下文保留/重建、失败回滚、dispose 清理；E2E 三运行时分别覆盖。 |
| P1-2 | P1 | 兼容/数据 | v0.2 允许 `session_create.provider_id` 存在但 `model` 为空（后端 `if let Some(model)` 才校验）；v0.5 的旧会话补选只覆盖“无 `provider_id`”的会话，且“已选会话再传 `model` → `invalid_value`”。这类历史会话（有 provider_id、无 model）没有补选 model 的路径，会继续用默认模型或失败。 | ADR §2.1-4:79、§3-4:152；设计 D6:422、D7:487；需求 v0.14 旧会话补选口径；v0.2 行为（代码现状 `session_backend.rs` 条件校验） | 在 v0.6 明确：`sessions.model` 为空时，即使已有 `provider_id`，也允许 `session_send.model` 补选（仅一次）；或启动迁移/只读策略。补 v0.2 会话样本测试（provider_id 有、model 空）。 |

### 2.2 P2（优化建议）

| 编号 | 级别 | 类型 | 问题 | 依据 | 建议 |
|---|---|---|---|---|---|
| P2-1 | P2 | 设计/边界 | `session_send` 的 `provider_id`/`model` 组合未完全定义：只传 `model`（无 provider_id）、只传 `provider_id`（sessions.model 空）、已有 provider_id 但 model 空、已有 provider_id 且 model 非空等分支，除文字描述外缺少真值表。 | ADR §2.1-4:79、§3-4:152；设计 D6:422、D7:487 | 补一张 `provider_id × model × sessions.model` 真值表（允许/拒绝/错误码），实现与 E2E 逐行覆盖。 |
| P2-2 | P2 | UI/状态 | `SessionSummary.provider_state` 只有 `active/invalid/readonly`，没有“provider 有效但 model 缺失/停用”的状态；v0.2 的“provider_id 有、model 空”会话在 UI 上可能显示 active，无法提示补选 model。 | ADR §2.1-4:79；ADR-010 B.4 `provider_state`；设计 D7:488 | 增加 `model_state`（或扩展 `provider_state` 取值）与 UI 提示；或明确只读/补选策略。 |
| P2-3 | P2 | 设计/措辞 | D10 仍写 `api_key` 本体“测试夹具 0 命中”，而 ADR §2.4 允许测试代码/合成 key 白名单；两处扫描口径不一致。 | 设计 D10:590；ADR §2.4:142-145；P1 计划 DoD 7:292 | 将 D10 改为“非测试源码/运行产物 0 命中；测试代码/合成 key 白名单除外”，与 §2.4/证据口径一致。 |
| P2-4 | P2 | 设计/兼容 | 已选会话的 `model` 后续被停用/删除时，`session_send` 只校验 provider 状态，不校验 model；没有补选/只读路径。 | ADR §2.1-4:75/79；设计 D7:487 | 明确 model 失效后的会话状态/错误；或把 model 校验纳入每次 run 前置检查。 |
| P2-5 | P2 | 验证/计划 | `verify:m7-10` 仍未定义；P1 计划 M8-03 仍写 M7-10“证据归档后补索引”。 | ADR §7-7:293；P1 计划 M8-03:392/398 | 实现时新增 `verify:m7-10` 或记录等价命令；M7-10 证据归档后补 M8-03 索引。 |
| P2-6 | P2 | 设计/清理 | D10:590 仍保留“不经适配器注入（消费映射见下一条）”的旧措辞，与 D10:591/592 的 spawn env/ Broker 注入并存，容易被误读。 | 设计 D10:590-592 | 改为“keychain 写入路径不在 provider 命令内注入；消费映射见下一条”，把“写入”和“消费”分开表述。 |

## 5. 需修改者明确

1. **旧会话补选适配器语义**：Codex/DSH 在补选时是创建 per-session 配置并保留原生上下文，还是重建原生会话？Claude 是否允许不同 provider 继续原生会话？需产品/架构确认。
2. **v0.2 provider_id+model 空会话**：允许 `session_send.model` 一次性补选，还是启动迁移/只读？需产品确认。
3. **model 停用后的已有会话**：按 provider 失效同样只读，还是允许补选 model？需产品确认。
4. **`session_send` 参数真值表**：provider_id/model 组合的允许/拒绝/错误码；建议在 D7 明确。
5. **`provider.catalog.get` 错误 data**：`error.data.aether_code` 是否登记为 D6 错误 data 约定（不新增错误码）；建议在 D6/ADR-006 注明。
6. **`verify:m7-10`**：实现时新增脚本或等价命令；证据记录。
