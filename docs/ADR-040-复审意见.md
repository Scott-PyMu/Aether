## 1. 总体结论

### 1.1 文档完整性

**良好。** v0.2 已形成“背景/假设 → 唯一决策 → 选择性计划/严格匹配表 → 状态机/写门 → 后台/周期/标志 → `health`/UI/指标 → sidecar 格式 → 安全/残余风险 → 实施/DoD/性能/no-go → 基线/契约 → G13/任务 → 失效/回退 → 签核/变更记录”的完整闭环；首轮指出的“验证链路、主库漏检、标志语义、G13 范围”等关键缺口均已在文本中落位。

### 1.2 一致性状态

**基本一致，但仍有 6 个交付口径需要闭环：**

1. **周期完整检查调度（P0-1）**：ADR 的残余风险承诺“应用持续运行…最长 7 天”，但 `full_check_due` 只在启动时评估，当前无运行期 7 天调度；持续运行会话可能长期不做 `integrity_check`，与 §3.2/产品 Q4 的安全窗口不一致。
2. **验证资产一致性**：ADR 要求 M10-14 后复跑 `verify:m10-10`，但现有 `scripts/test/m10-10/verify-m10-10.mjs` 明确断言 `!layout.includes("dirty_shards")` 和 `full_startup_plan(layout, "fingerprint_mismatch")`，标签为“ADR-039，非 ADR-040”；`apps/desktop/src/m10_10_storage_check.test.tsx` 的 fixture 仍只有旧字段。M10-14 DoD-9 可能“表面通过、实际未验证”或直接失败。
3. **`health` 兼容性**：`checked_shards` 从“全部分片中已完成数”变为“本轮计划中实际完成数”，`state=ok` 从“全量检查通过”变为“本轮计划完成”；ADR 只说明“旧客户端忽略未知字段”，但既有字段语义变化未做兼容说明。M10-03 的 HTTP/WS/CLI 外部消费者可能误读。
4. **残余风险验收措辞**：§3.2 既说“发现前仍可写”，又说“写入不得静默成功或扩大可恢复范围”；§3.3/DoD-5 以“损坏片写入不静默成功”为通过条件。SQLite 在损坏页未被触及时可能成功写入其他页，该条件不可普遍验证；需要改为可执行的故障注入判据。
5. **性能 no-go 与目标不一致**：§4.3 目标为 dirty 1/2 ≥30%、dirty 4 ≥10%、dirty 8 劣化 ≤5%；no-go 只写 dirty 1–2 <20%，dirty 4/8 未纳入，20–30% 存在空档。产品 Q5 已确认“补齐 no-go”，但 v0.2 尚未更新。
6. **周期完整检查基线可能饥饿**：D-040-3 §3 将 `last_full_check_at=None` 的首次基线绑定到“首个严格干净启动”；若用户持续异常启动（选择性/全量回退），可能永远没有严格干净启动，7 天/20 次计时不启动，第二层 `integrity_check` 兜底无法保证。

### 1.3 最大风险

1. **P0-1 周期完整检查调度缺失**：`full_check_due` 只在启动时评估，没有运行期 7 天定时器；§3.2 却承诺“应用持续运行…最长 7 天”。持续运行会话可能长期不做 `integrity_check`，产品 Q4 的残余风险接受基于不成立的窗口。
2. **M10-14 验证资产未更新**：`verify:m10-10` 仍按 ADR-039 全量口径断言；`m10_10_storage_check.test.tsx` 未列修改范围。若 M10-14 直接实施，DoD-9/§6 的“复跑 `verify:m10-10`”可能失效，G13 证据链不完整。
3. **外部客户端误读 `health`**：`checked_shards=2/8 + state=ok` 在旧客户端可能显示“2/8 完成”或“检查未完成”；`full_coverage` 新字段对旧客户端不可见。
4. **残余风险故障注入不可判定**：若“写入不静默成功”按字面执行，可能因 SQLite 写入未触及损坏页而失败；若放宽，又无法证明“不扩大损坏”。需要定义“写损坏页/写其他页”的区分。
5. **§4.3 验收空档**：dirty 4/8 未纳入 no-go，dirty 1–2 在 20–30% 之间归属不明；M10-14 可能以“部分收益”实施。
6. **周期完整性基线饥饿**：持续异常启动时 `last_full_check_at` 可能永远为 `None`，`integrity_check` 基线/7 天计时不启动；残余风险的第二层兜底失效。

### 1.4 安全专项

未发现“把权限控制误述为沙箱”；ADR-040 不新增外部信任边界、命令面、事件、设置键、迁移或第三方依赖。**但 P0-1 直接影响产品 Q4 的残余风险接受：如果“最长 7 天”没有运行期调度支撑，Q4 的接受窗口不成立，安全/QA 不能据此签核。** 当前还缺**可执行的故障注入判据**和**签核记录**；P0-1/P1-3 闭环后，§3.2 的残余风险表述才可作为安全/QA 签核输入。

## 4. 风险清单

### P0（签署/实施前必须闭环）

1. **P0-1 周期完整检查没有运行期 7 天调度**：`full_check_due` 只在启动时评估；持续运行超过 7 天不会触发 `integrity_check`，与 §3.2“最长 7 天”承诺/产品 Q4 接受窗口冲突。

### P1（签署前必须闭环）

1. **P1-1 验证资产未更新**：`verify:m10-10` 仍断言 ADR-039 全量口径；`m10_10_storage_check.test.tsx` 未列入修改范围；DoD-9 的“复跑”可能失去意义或失败。
2. **P1-2 `health` 既有字段语义变化**：`checked_shards`/`state=ok` 对旧客户端/外部消费者的含义变了；只靠“忽略未知字段”不能解决。
3. **P1-3 残余风险验收措辞不可执行**：“发现前仍可写”与“写入不得静默成功”矛盾；故障注入需区分损坏页/其他页，否则无法签核。
4. **P1-4 §4.3 no-go 不一致**：dirty 4/8 未纳入 no-go，dirty 1–2 存在 20–30% 空档；产品 Q5 已确认补齐，v0.2 未更新。
5. **P1-5 周期完整检查基线饥饿**：`last_full_check_at=None` 只绑定首个严格干净启动；持续异常启动时 7 天/20 次完整性检查可能永不触发。

### P2（不阻塞文本方向，随 v1.0/设计 v1.36 处理）
