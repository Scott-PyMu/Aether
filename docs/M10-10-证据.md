## 3.1 `storageCheck` 波动诊断

`m10_10_check_diag`（8 个分片，`quick_check`）：

```text
mmap 前顺序第一轮: 12.1–13.6 s
mmap 前顺序第二轮:  9.9–12.7 s
mmap 前 8 并发墙钟: 31.69 s
mmap 512MiB 后顺序: 4.9–8.3 s
mmap 后 8 并发墙钟: 10.64 s
```

结论：

- 8 个 `quick_check` 并发读取约 5.25 GiB，**总吞吐不随并发线性扩展**；SATA SSD/CPU 队列饱和。mmap 后并行墙钟从 31.69s 降至 10.64s，产品 storageCheck 两次 15.78s/15.93s。
- 冷缓存、Windows Defender/索引、Electron/启动尾段并发 I/O 仍会叠加，但 mmap 后波动已缩小到约 1s。
- 这不是单库损坏或锁等待；顺序两轮均通过且单片耗时稳定，说明是 I/O/CPU 资源竞争与缓存状态。

**对主界面的影响**：

- `uiReadyAt` 由壳层在 renderer 加载后标记，不等待 `quick_check`；实测主 workbench 约 0.5–1.5s 出现，**不会停在调试/启动页**。
- `health.storage_check.state=checking` 时写门为 `checking`；读和 UI 可用，事件写入被拒绝；检查通过后恢复。
- 若 health 本身超过 15s 无响应，`HealthMonitor` 会显示“core 无响应”提示（主界面内），不是 S-12 调试页。
- 若检查失败：`storage_state=persist_degraded`，主界面显示只读降级提示；当前 S-00 进度条/S-08 完整原因页仍未实现，但不会把主界面锁死到调试页。

## 3.2 优化方案与参考实现

已实施：只读连接 `mmap_size=512MiB`（`pragma::apply_read_only`），`m10_10_check_diag` 并行墙钟 31.69s → 10.64s，产品 core `storageCheck` 15.78/15.93s。

参考本机 `E:\hermes-studio` / `E:\Proma`（只读参考，不复制代码）：

- Hermes Studio：打开 WAL + `synchronous=NORMAL` + migration，不在每次启动做全库 `quick_check`；迁移失败走 `quarantineForRebuild`/恢复，不阻塞 UI。
- Proma：会话主要为 JSONL，SQLite 仅用于 planning 且延迟打开；启动 splash/runtime init，无全库 integrity scan。

候选优化（需 ADR/任务授权）：

1. **脏分片选择性检查**：非严格 sidecar 启动时只检查 header/file/WAL 变化的分片；其余沿用 sidecar 指纹，预计 1 个分片 5–8s。
2. **周期完整检查**：每周 `integrity_check`/20 次启动完整检查，后台执行；记录 `last_full_check_at`，不在每次启动全扫。
3. **设备自适应并发**：NVMe 8 / SATA SSD 4 / HDD 2；当前固定 8，8 并发已观察到 SATA SSD 饱和。
4. **I/O 优先级**：后台检查低优先级，延迟到首屏/health 之后（当前已由首个 health 触发）；Windows Defender 排除数据目录。
5. **按分片写门**：已检查分片先放行，未检查分片排队/拒绝；UI 显示 `checked_shards/total_shards`，避免“整机写门等待”。
6. **数据目录放置 NVMe**：M10-08 参考 NVMe 19.36s；本机 SATA SSD 是波动主因。

## 4. 故障注入

| 注入 | 测试 | 结果 |
|---|---|---|
| 备份中持续写入 | `m10_09_sharding backup_under_write_pressure_drains_and_preserves_events` | 500 事件写入中执行备份；drain 后 queue depth=0；备份 manifest/validate 通过；恢复写入后 500 事件全保留 |
| 恢复进程 kill | `m10_10_restore_kill restore_kill_leaves_old_generation_and_cleans_staging` | 子进程 staging 中 kill；`CURRENT` 仍为旧 generation；staging 清理；旧库保留 |
| Windows `CURRENT` 替换失败 | `m10_09_sharding current_replacement_failure_keeps_old_pointer` | 只读 `CURRENT` 替换失败；旧指针内容保持 `old` |
| WAL 非 0 / sidecar | `m10_10_startup` | WAL 写入后 `clean_shutdown_is_strict=false`，强制后台检查 |
| 备份维护 drain | `m10_09_sharding maintenance_pause_blocks_writes_until_resume` | 暂停后 append 阻塞；Drop 后成功 |

> Windows 直接 `ReplaceFileW`/`MOVEFILE_WRITE_THROUGH` 调用仍受 workspace `unsafe_code = "forbid"` 限制；本测试注入的是替换失败路径（只读目标），不是 API 级失败。
