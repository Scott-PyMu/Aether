## 3.1 `storageCheck` 波动诊断

`m10_10_check_diag`（8 个分片，`quick_check`）：

```text
顺序第一轮每片: 12.1–13.6 s（冷/热前）
顺序第二轮每片:  9.9–12.7 s（OS 缓存变暖）
8 并发每片:     10.7–31.7 s
8 并发墙钟:     31.69 s
```

结论：

- 8 个 `quick_check` 并发读取约 5.25 GiB，**总吞吐不随并发线性扩展**；SATA SSD/CPU 队列饱和后，单片耗时从约 12s 升到 25–32s。
- 冷缓存、Windows Defender/索引、Electron/启动尾段并发 I/O 会叠加；因此同一机器观测到 23.4s / 34.6s 的波动。
- 这不是单库损坏或锁等待；顺序两轮均通过且单片耗时稳定，说明是 I/O/CPU 资源竞争与缓存状态。

**对主界面的影响**：

- `uiReadyAt` 由壳层在 renderer 加载后标记，不等待 `quick_check`；实测主 workbench 约 0.5–1.5s 出现，**不会停在调试/启动页**。
- `health.storage_check.state=checking` 时写门为 `checking`；读和 UI 可用，事件写入被拒绝；检查通过后恢复。
- 若 health 本身超过 15s 无响应，`HealthMonitor` 会显示“core 无响应”提示（主界面内），不是 S-12 调试页。
- 若检查失败：`storage_state=persist_degraded`，主界面显示只读降级提示；当前 S-00 进度条/S-08 完整原因页仍未实现，但不会把主界面锁死到调试页。

## 4. 故障注入

| 注入 | 测试 | 结果 |
|---|---|---|
| 备份中持续写入 | `m10_09_sharding backup_under_write_pressure_drains_and_preserves_events` | 500 事件写入中执行备份；drain 后 queue depth=0；备份 manifest/validate 通过；恢复写入后 500 事件全保留 |
| 恢复进程 kill | `m10_10_restore_kill restore_kill_leaves_old_generation_and_cleans_staging` | 子进程 staging 中 kill；`CURRENT` 仍为旧 generation；staging 清理；旧库保留 |
| Windows `CURRENT` 替换失败 | `m10_09_sharding current_replacement_failure_keeps_old_pointer` | 只读 `CURRENT` 替换失败；旧指针内容保持 `old` |
| WAL 非 0 / sidecar | `m10_10_startup` | WAL 写入后 `clean_shutdown_is_strict=false`，强制后台检查 |
| 备份维护 drain | `m10_09_sharding maintenance_pause_blocks_writes_until_resume` | 暂停后 append 阻塞；Drop 后成功 |

> Windows 直接 `ReplaceFileW`/`MOVEFILE_WRITE_THROUGH` 调用仍受 workspace `unsafe_code = "forbid"` 限制；本测试注入的是替换失败路径（只读目标），不是 API 级失败。
