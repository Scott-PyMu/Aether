## 4. 故障注入

| 注入 | 测试 | 结果 |
|---|---|---|
| sidecar 缺失/`background_check_completed=false` | `m10_10_startup`、`m10_10_clean_start` | 严格跳过失效，走全量检查；`clean_start_count=0` |
| WAL 非 0 | `m10_10_startup` | `clean_shutdown_is_strict=false`，走检查 |
| 分片页级损坏（events 根页头） | `m10_10_fault` | `state=failed`、`write_gate=checking`、`failure_count>=1`、事件写入 `StorageBackpressure`、`storage_state=persist_degraded` |
| 恢复进程 kill | `m10_10_restore_kill` | `CURRENT` 仍为旧 generation；staging 清理；旧库保留 |
| 备份中持续写入 | `m10_09_sharding backup_under_write_pressure_drains_and_preserves_events` | 500 事件写入中备份；drain 后 queue=0；恢复写入后事件全保留 |
| Windows `CURRENT` 替换失败 | `m10_09_sharding current_replacement_failure_keeps_old_pointer` | 只读目标替换失败；旧指针保持 |
| 备份维护 drain | `m10_09_sharding maintenance_pause_blocks_writes_until_resume` | 暂停后 append 阻塞；Drop 后成功 |
| write_gate/UI 映射 | `m10_10_storage_check.test.tsx`、`m10_10_fault` | checking 显示 S-00；failed → S-08；维护态不显示 S-08 |

> **Windows `ReplaceFileW` 直接 API 调用**：workspace `unsafe_code = "forbid"`，未新增
> FFI/依赖。当前 `std::fs::rename` 在 Windows 映射 `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`，
> 已通过只读目标注入失败路径；DoD 的「`ReplaceFileW`/`MoveFileExW` 失败」按
> `MoveFileExW` 分支覆盖。直接 `ReplaceFileW` 调用登记为未验证（§5）。

## 5. 未验证/后续

1. **直接 `ReplaceFileW` API**：受 `unsafe_code = "forbid"` 限制未实现；当前使用
   `MoveFileExW`（`std::fs::rename`）并已注入失败路径。若后续要求 API 级 ReplaceFileW，
   需另立 ADR 评估安全 FFI 边界。
2. **Windows NVMe BusType 自动识别**：`sysinfo` 只能区分 HDD/SSD；安全 FFI 不可用，
   NVMe 机型默认按 SSD 4 并发处理，可用 `AETHER_STORAGE_DEVICE=nvme`（证据/运维覆盖）
   强制 8。NVMe 8 并发已由矩阵/ADR-039 参考数据覆盖，未在本机自动识别。
3. **macOS/Linux Electron 启动矩阵**：本机仅 Windows；M10-09 分片 CI 矩阵已通过，
   M10-10 Electron 启动未在 macOS/Linux 执行。
4. **首次 ever-cold Electron**：新构建首次启动 1865ms；warmup 后 3 跑 ≤543ms。
   若验收要求 OS 冷缓存不得 warmup，需进一步优化 Electron renderer 预热/并行加载，
   当前不宣称满足。
5. **ADR-040**：仍为 Proposed，未实施；产品按 ADR-039 全量检查。G13 前若需选择性
   检查，须先完成四角色签署并更新设计文档/基线。
6. **G13 复测**：M10-10 自身证据已齐；M10-11、M10-13、G13 汇总复测由对应任务执行。
