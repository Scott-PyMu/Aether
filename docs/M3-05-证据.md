## 1. 契约登记（实现增量，非设计偏离）

### 1.1 诊断包（`export_diagnostics`；D11）

| 项 | 值 |
|---|---|
| 产物 | `<target>/aether-diagnostics-<ts>.json`（单 JSON；同毫秒冲突追加 ULID 尾缀）；D11 未规定容器格式，单文件便于脱敏扫描与归档 |
| 段 | `bundle_version`、`generated_at`、`app`（app/core/线协议版本）、`host`（os/arch/data_dir）、`health`（`HealthReport` 同形状）、`security`（级别/说明）、`capacity`（db/wal/阈值/等级）、`store`（schema 版本 + 关键表行数）、`config.settings`（脱敏后的持久化设置）、`logs`（环形缓冲行数/文件路径/文本）、`task_dumps`（M2-05 缓冲）、`notes`（缺段原因） |
| 脱敏 | 整包经 `aether_security::Redactor::redact_json` 递归脱敏后**再扫描**（`is_clean`）；任一命中 → `internal` 拒绝写出（D10 可判定口径） |
| 空间护栏 | 与备份同口径（ADR-003 决策 19）：目标可写 + 可用空间 ≥ `db+wal`×1.2；不足 → `diagnostics_space_insufficient`（消息内稳定业务码） |
| 响应 | `{ path, file_name, bytes, generated_at, sections[], scanned_clean:true, log_lines, task_dumps }` |
| 降级态 | 启动失败/降级启动（无读连接）：仍可导出（健康/安全/容量/日志齐备；`store=null`、`config.settings=null`、`notes` 记缺段原因，D4） |

### 1.2 `backup_list.reminder` 段（D13；M3-05 增强）

`{ enabled, due, last_backup_at, since_ms, threshold_ms:604800000, reason:"never"|"stale"|null }`

- `enabled` 读取设置键 `backup.reminder`（缺省 `true`）；
- `last_backup_at`/`since_ms` 由核心注入时钟计算（`ManualClock` 可注入；`threshold_ms` = 7 天）；
- 容量段由诊断后端按注入的 `CapacityConfig` 重算（与诊断包同一实例）。

### 1.3 设置键（Q9/Q10 登记）

| 键 | 类型 | 缺省 | 语义 |
|---|---|---|---|
| `backup.reminder` | bool | `true` | 7 天未备份提醒全局开关（D13「可关闭」） |

写入经单写队列（`StoreCommand::UpsertSetting`，AGENTS §2.4）；读经读连接池；未登记键 `invalid_enum`；值类型不符 `invalid_type`。工作区绑定键（M3-08）未登记。

### 1.4 容量阈值参数化（DoD2）

- `CapacityConfig { warn_bytes, critical_bytes }`（默认 2GiB/5GiB，D13）；
- 生产构造可经环境变量覆盖（`AETHER_CAPACITY_WARN_BYTES` / `AETHER_CAPACITY_CRITICAL_BYTES`，仅调参、语义不变；常量级调参记录于此）；
- 测试经 `with_capacity_config` 显式注入；输出三档 `ok|warn|critical` 进入 `backup_list.capacity.level` 与诊断包 `capacity.level`。

### 1.5 安全级别（D10/A3；S-05）

- `run()` 启动时执行 A3 自检（OS 凭据库写→读→删测试项，`aether_security::self_check`），结果经 `startup_get` 快照的 `security_level:{level:"os"|"degraded",detail}` 暴露；设置页只读展示（`data-level`）；
- 诊断包导出时复采一次进入 `security` 段；
- 边界：P0 无密钥消费路径，本任务只判定级别，不挂载 A3 加密文件/不索取口令；**完整降级挂载（口令 + `secrets.enc`）与「安全级别：降级」联动为 M3-11 handoff**（首个 keyring 写入路径为 M3-11 供应商 `api_key`，ADR-010；见 §4.2/§5）。

### 1.6 `export_diagnostics` 目标路径语义（§4.4）

命令层由 `validate_user_path(allowed_roots)` 改为 `path::validate_backup_target_dir`（绝对路径 + Windows 特殊形态拒绝 + canonicalize + 存在目录），与备份外部路径一致（ADR-003 决策 19「导出到外部路径；不做默认目录信任」）。`ipc_validation` 中毒化样本同步更新（见 §4.4），并新增更严拒绝样本（不存在目录、非目录文件）。

## 4. 边界与偏离记录

1. **E2E 分层口径（与 M3-03/M3-04 一致）**：诊断导出链路由 (a) 命令层 mock invoke（外部目标 canonicalize / 非法目标 0 下游调用 / 设置键白名单）与 (b) 后端直连（真实存储 + 真实脱敏 + 真实日志汇聚端）证明。真实系统目录选择器对话框与真实 WebView 内联回环归 M4-05（窗口化冒烟与内联权限回环 E2E 的承接声明同 M3-12 口径）。
2. **安全级别仅判定、不挂载加密文件（M3-11 handoff）**：P0 无密钥消费路径，本任务只做级别判定与只读展示。**首个 keyring 写入路径为 M3-11**（供应商 `api_key`；ADR-010 其 DoD4 明确「A3 降级走加密文件」）；完整降级挂载（口令 + `secrets.enc`）与「安全级别：降级」的联动随 M3-11 接线并以其任务证据为准（若口令输入流程未纳入 M3-11 范围，须在该任务评审登记；见 §5）。测试注入 `StaticSecurityProbe`，不触碰真实 OS 凭据库；生产 `run()` 每次启动执行一次 A3 自检（A3 设计口径）。
3. **启动快照新增可选字段**：`security_level` 为附加字段（`skip_serializing_if`；测试构造的门缺省不输出，前端显示 `unknown`，不伪造级别）。既有启动相关测试无精确 JSON 断言，全量回归通过。
4. **`export_diagnostics` 目标校验语义调整（本任务登记）**：M1-08 时 `allowed_roots` 为空占位且代码注释明确「路径白名单根目录随 M3-05（诊断导出）接入」；本任务按 ADR-003 决策 19 落地为**外部路径语义**（与 `backup_create.target_dir` 一致，不做默认目录信任）。`ipc_validation` 的两个毒化样本随之更新：其一为「不在白名单的已存在目录」（`outside`）；其二为遍历样本（`root/../outside`，新契约下 canonicalize 到外部已存在目录即合法，不再作为拒绝样本）。两者替换为**不存在目录**与**非目录文件**，并在合法样本中新增外部目录与已登记设置键；同时保留 `validate_user_path`（默认拒绝实现）与 `allowed_roots` 访问器供白名单类命令后续复用。该变更涉及 M1-08 冻结校验矩阵的样本语义（非静默修改），随本任务证据提交评审确认；拒绝样本（相对路径、Windows 特殊形态、不存在/非目录）与合法样本均有覆盖（`ipc_validation` 9/9 通过）。
5. **容量阈值参数化**：经构造注入或环境变量覆盖（常量级调参，§1.4 记录）；`ok|warn|critical` 三档语义与 M3-04 `backup_list` 完全一致。**「每小时容量巡检」（D13）的巡检节奏口径不由本任务自行认定**，列为 Gate 3 待裁定项（见 §6）；本任务交付阈值与等级语义，不改变巡检触发方式。
6. **诊断包为单 JSON**：D11 未规定容器格式；单文件便于「脱敏 → 再扫描 0 命中」守门与证据归档。日志段受环形缓冲上限（2000 行）约束。
7. **`settings-security-level` 的 `unknown` 态**：仅出现在未经 `run()` 启动探针的测试/嵌入构造；生产路径必有 `os|degraded`。
8. **`DiagnosticsControlBackend` 位于装饰器链内层**：`SessionBackend` → `DiagnosticsControlBackend` → `BackupControlBackend` → `RuntimeControlBackend` → 存储/健康；`backup_list` 的容量段与 `reminder` 由诊断后端统一重算/追加（单一事实源），其余命令显式透传。
9. **容量巡检当前实现为按需投影（口径待裁定）**：容量统计在 `backup_list` 查询时经 `db+wal` 文件大小投影（D13 阈值语义不变；页面打开/刷新与导出前触发）；D13 字面要求的「每小时巡检」是否由该实现满足，**不属本文件自行认定范围**，列为 Gate 3 待裁定项（事实、约束与裁定选项见 §6）。

## 6. Gate 3 待裁定项：容量巡检口径

> 本节登记性质为**评审事项**（不构成设计变更，不升版设计文档）；裁定结论应由 Gate 3 评审记录并回流本证据文件/后续任务。

**待裁定问题**：D13 实现要点写明「**每小时容量巡检**；巡检统计 db+wal 大小，2GB 警告 / 5GB 强烈提示」。M3-05 的交付（DoD2）为**阈值参数化 + 等级投影 + 横幅联动**：容量在 `backup_list` 查询时（页面打开 / 刷新 / 导出前）按 `db+wal` 文件大小即时统计，未实现独立的后台每小时巡检任务。

**事实与约束**：

- P0 命令面（35 条目 / 36 命令，D7/ADR-004/006/007/010）与附录 B 事件清单为冻结基线；现有条目中没有可承载「后台巡检触发 → 用户可见通知」的命令/事件类型；
- D13 阈值语义（2GB/5GB、`ok|warn|critical`）已交付并通过 DoD2 证据（注入阈值模拟三档 + UI 横幅）；
- 既有 `ResourcePatrol`（M2-07）为 RSS 资源巡检，不统计容量；`tracing` 汇聚端（M2-07）可承接巡检日志，但当前无 UI 通知通道；
- 延迟风险面：用户长期停留单一界面且不触发容量查询时，告警可能延迟到下一次查询/页面打开；不产生数据损坏（阈值仅提示，不触发自动动作）。

**裁定选项（供 Gate 3 选择）**：

1. **接受按需投影为 P0 口径**：将 D13「每小时」解释为采集频率目标而非硬性 P0 要求，在 Gate 3 记录该口径（不新增机制，改动最小）；
2. **要求补齐每小时巡检**：实现为「后端后台任务（**只落 `tracing` 巡检日志，事件清单冻结下用户可见通知无载体**）+ 前端定时查询投影」；**如需用户可见通知，必须先行 ADR 扩展附录 B 事件清单后再排期**；
3. **顺延 P1**：随 D13 保留策略/自动备份一并实现（D13 失效条件为「库 >5GB 或事件增长 >500MB/月」）。

**本任务立场**：现状交付对应选项 1；在 Gate 3 裁定前，本文件不主张「每小时巡检」已完成（§4.5/§4.9 措辞已按此校正）。

**DoD 关系**：无论裁定结果，DoD1–4 已满足，本项不构成本任务 DoD 缺口。
