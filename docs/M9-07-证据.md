## 2. 实现摘要

### 2.1 进程结构与启动序列

- `apps/desktop/electron/app.ts`（main）：
  - 单实例 `app.requestSingleInstanceLock()`；`second-instance` 聚焦当前窗口（S-12/S-13 优先）；
  - 先 `createSecureWindow` + 加载 `startup/startup.html`（S-00），等待 `ready-to-show`（≤1.5s），
    再 `startDaemonForWindow` → `runStartupSequence`；
  - `initialize` 目标 2s、硬超时 10s（`MIN_INITIALIZE_HARD_TIMEOUT_MS`），超时 kill + `waitForExit` 后重试 1 次；
  - 预 `initialize` 首帧 error → S-12；`sync_dir_blocked`→`a4_blocked`、`data_dir_locked`、
    `db_open_failed`、`schema_checksum_mismatch`；进程退出/ENOENT→`daemon_start_failed`；
  - `degraded`/`quick_check` 失败**不**走 S-12（主 UI 继续加载，S-08 由既有 health 呈现）；
  - 关闭：`before-quit` 先 `shutdown`（8.2s）+ 等退出（1.3s）+ 强杀兜底；完整 T11/M9-09 预算由 M9-09 收口；
  - `app_restart`：`app.relaunch()` + 关闭序列；E2E 实测第二进程启动。
- `apps/desktop/electron/daemonClient.ts`：JSON-RPC 2.0 over JSONL；2MiB 帧上限；id 匹配；
  `aether.event`/`daemon.status` 通知；stderr 200 行环形缓冲；超时/退出拒绝全部在途请求。
- `apps/desktop/electron/startup.ts`：启动状态机（纯 TS，可单测）；`StartupSuccess/Failure` 携带 client，
  最多 2 次尝试；窗口先于 daemon 的硬断言。
- `apps/desktop/electron/daemonPaths.ts`：`AETHERD_BIN` → 打包 `resources/bin/aetherd` → `target/{release,debug}`；
  `AETHERD_EXTRA_ARGS` 仅 E2E 注入。
- `scripts/ci/electron-bin.mjs`：开发/E2E 在 Windows 上把冻结的 `electron.exe` 硬链接为同目录
  `Aether.exe`（产品打包名），避免受限沙箱/单实例管道冲突；E2E/dev userData 放 `dist-out/`。
  **不改变 Electron 版本/生产入口**；详见 §4.1。

### 2.2 preload / IPC

- `preload.ts`：`contextBridge.exposeInMainWorld("aether", Object.freeze(api))`，恰好
  `rpc`/`onEvent`/`offEvent`/`pathForFile`/`version`；不暴露 `ipcRenderer`/`require`/`process`/`fs`。
- `pathForFile` 在 preload 内调用 `webUtils.getPathForFile(file)`，只返回路径字符串（ADR-029 P1-7）。
- `rpc` 返回**可克隆信封** `{ok:true,result}` / `{ok:false,error:{code,message,data}}`：
  `contextBridge` 跨隔离世界只保留标准 `Error.message`，自定义 `aether_code`/`business_code` 会丢失；
  M9-08 typed client 负责把错误信封转换为 `AetherError { aether_code, business_code?, details? }`。
- main `ipcMain.handle("aether:rpc")`：sender 必须是主窗口；method 必须在
  `packages/protocol/src/command-manifest.json` 的 63 条内；params ≤2MiB；并发 ≤64；
  4 条壳本地命令本地处理，其余 59 条转发 daemon；daemon 不可用返回 `core_not_ready`。
- 事件：daemon `aether.event` → `MainEventBridge`（M9-05：单通道 FIFO/16ms/4096/3 次补读升级）
  → `webContents.send("aether:event")`；`messages_page` 作为 journal 补读。

### 2.3 S-12 独立 renderer / 离线诊断

- `fatal/fatal.html` + `fatal/fatal.js` + `fatalPreload.ts`：独立窗口、独立 preload；
  主 UI preload 不加载（E2E 断言 `typeof window.aether === "undefined"`）。
- 锚点：`shell-fatal`/`-reason`/`-log-path`/`-data-dir`/`-retry`/`-exit`/`-export-diagnostics`/
  `-manual-move`；`data-reason` 六值；`data-result`（导出）。
- `offlineDiagnostics.ts`：不依赖 daemon，收集 shell.log、aetherd.log 尾、daemon stderr、版本/平台/路径/
  环境变量（脱敏），写 `aether.shell-diagnostics.v1` JSON；密钥/令牌经 `redact.ts` 处理。
- 重试：关闭 S-12 窗口 → 重新创建主窗口/S-00 → 重新启动 daemon；E2E 用 `bootstrap_once` 验证成功回主 UI。
- `keychain/keychain.html` + `keychainPreload.ts`：S-13 锚点/`data-scope`/`data-mode` 已交付；
  **触发与真实 Keychain preflight 属 M9-09**（本任务 `showKeychainPrompt` 已导出，动作未接线）。

### 2.4 壳本地命令

- `shellLocal.ts`：严格 DTO（`deny_unknown_fields` 语义）：
  - `app_exit`/`app_restart`：必须 `confirm:true`；返回 `{exiting}`/`{restarting}`，响应后执行退出/重启；
  - `ref_pick`：`{kind:"file"|"directory"}`；对话框取消 → `{path:null}`；
  - `startup_pick_target`：省略/`null`/`{}` 等价；取消 → `{target_dir:null}`；
  - 返回值 `realpathSync.native` canonicalize + `statSync` 文件/目录校验；失败 `path_rejected`。
- 路由：63 = 59 daemon + 4 shell；`startup_get`/`startup_migrate` 保留不暴露（61/63）。

### 2.5 安全基线（M9-07 范围）

- 生产 renderer 经自定义 `aether://app` 协议加载 `apps/desktop/dist`，响应头下发生产 CSP；
  dev 仅额外允许 Vite HMR 的 `127.0.0.1:5173`。
- `webPreferences`：`nodeIntegration:false`、`contextIsolation:true`、`sandbox:true`、`webSecurity:true`、
  `allowRunningInsecureContent:false`、`webviewTag:false`、`experimentalFeatures:false`。
- `setWindowOpenHandler`/`will-navigate`/`will-attach-webview`/`setPermissionRequestHandler`/
  `setPermissionCheckHandler` 全部接线；外链 `shell.openExternal`；E2E 模式只记录不拉起浏览器。
- `@electron/fuses`、WebContentsView、路径命令全集、SBOM 属 **M9-10**；打包/签名属 **M9-11**。

## 4. 环境限制与未验证

### 4.1 Electron 45.0.0 在受限 Windows 沙箱下的启动限制（已定位/已绕行）

- 冻结版本：`apps/desktop/package.json` 的 `electron: "45.0.0"`（精确），`verify:m9-01-baseline` 通过；
  本任务全部 E2E 最终在 **Electron 45.0.0** 上通过（`version()` 返回 `45.0.0`）。
- 本机（Windows 11 26200 + AI 工具受限账户）实测到两个**环境级**问题，不是应用代码缺陷：
  1. **沙箱初始化**：Electron 45 不带 `--no-sandbox` 时 `0x80000003`（STATUS_BREAKPOINT）；
     同机 Electron 44 正常。开发/E2E 以 `AETHER_NO_SANDBOX=1`（或 `AETHER_E2E_NO_SANDBOX=1`）
     显式启用 `--no-sandbox`（仅 dev/E2E；生产不设置）。
  2. **单实例锁**：受限账户下 Chromium 45 的 ProcessSingleton 只能在工作区内创建锁；
     userData 放在 `%TEMP%`/`%APPDATA%` 时 `requestSingleInstanceLock()` 崩溃或返回 false
     （`process_singleton_win.cc: Lock file can not be created: 拒绝访问`）。
     同时 `electron.exe` 名称会与单实例管道冲突；以产品名 `Aether.exe` 启动即正常。
- **已落地绕行**（`scripts/ci/electron-bin.mjs`）：
  - Windows 上把冻结的 Electron 二进制硬链接为同目录 `Aether.exe`（失败则复制）；
  - E2E/dev 的 userData 放在 `dist-out/`（工作区、已 gitignore）；
  - 仅 dev/E2E 设置 `AETHER_E2E_NO_SANDBOX=1`；
  - **不修改依赖版本/冻结面**；M9-11 打包后的真实可执行文件本就是 `Aether.exe`，不需要该绕行。
- 复跑结果：`pnpm e2e:m9-07` **37/37 PASS**、`pnpm e2e:m9-07:dev` PASS，均使用 45.0.0。
- 仍建议 CI/其他机器（正常桌面账户）复跑一次，确认沙箱无关性；该复跑不再阻塞本机结论。
