## 3. 压测口径

- **写**：10 并发（每会话 1 writer），D3 单写连接 group commit（16ms 或 ≥256 条），`journal_mode=WAL`、`synchronous=NORMAL`、`foreign_keys=ON`、`busy_timeout=5000`、`wal_autocheckpoint=1000`、`journal_size_limit=67108864`、`cache_size=-32000`、`temp_store=MEMORY`。
- **补读**：10 并发，`events_page`（`seq > after`，limit 50）、`messages_page`（limit 50）、`last_seq`（`MAX(seq)`）。
- **quick_check**：独立子进程打开 5.22 GiB 库 → D3 PRAGMA → `PRAGMA quick_check` → 迁移 checksum 校验；每 run 1 次，3 个 run 取中位/P95。
- **备份**：`VACUUM INTO` 5.22 GiB → 备份 `quick_check`。
- **恢复**：复制备份 → 打开 → `quick_check` → 迁移 checksum 校验。
- **增长**：写窗口每 10s 采样 `db+wal`；保留策略按 ADR-021（30 天，`message.delta`/`usage`/`log`，先归档后删除；批 ≤5000 行、rowid 精确删除、单批事务）在备份副本上模拟。
- **分片**：按会话 `session index % 8` 分片；同一数据集/机器/并发/时长；顺序 `quick_check` 总和与并行墙钟分别记录。
- **可重复性**：固定 seed、批大小、并发、时长；每次 run 复制源数据集，避免写压测污染 `dataset.json` 的 sha256/行数。

## 8. 保留策略（ADR-021 / D-038-4）

- 口径：30 天窗口；可清理类型 `message.delta`/`usage`/`log`；先归档后删除；批 ≤5000 行、按 rowid 精确删除。参考运行在 5.22 GiB 备份副本上采样 **50,000 行**（全量 14,684,946 行可清理），避免 5GB 全量清理占用数小时。
- 实测（run1）：采样 50,000 行耗时 **44,541.684ms**（**1,122.5 行/s**）；**批 P95 4,891.750ms / max 4,911.754ms**；线性外推全量清理约 **3.63 小时**。
- 页/文件：`page_count` 1,373,882；`freelist_count` 采样后仍很低（页复用/高水位），物理文件 **5.22 GiB** 不自动收缩；`projectedLiveBytes` 采样估算不可靠，改用类型分布计算。
- 12 个月投影（保守，按行数占比）：可清理行 15,998,813（80.0%），30 天保留后保留约 1,315,000 行；不可清理 4,001,187 行；投影 live rows 约 **5,316,000 行 = 26.6%**，折算 **1.387 GiB < 5 GiB**。
- 结论：**保留策略在容量上可把 live 数据压到 <5GiB**，但：
  1. 物理文件高水位仍 **5.22 GiB >5 GiB**，保留不自动收缩；
  2. 批清理 P95 **4.89s >500ms**（D3 单事务目标），全量清理约 **3.63h**；
  3. 产品 `select_retention_batch` 的 `ORDER BY rowid` 走 TEMP B-TREE（O(N²)），可能比采样更慢。
- 因此「保留单库 + 保留策略充分」**不能单独成立**；需启动优化 + 保留清理优化/分库（ADR-039）。

## 11. 未决风险与阻塞

1. **ADR-039 v1.0 已批准（2026-11-14），但分库/启动优化尚未实施（M10-09/10/11 待执行）**：当前产品在 5 GiB 库上仍会 `quick_check` >30s、`uiReadyAt` 未达标。G13 前必须完成 M10-09/10/11。
2. **分片本身不等于启动达标**：8 分片**顺序**检查总和 72.9s 仍 >30s；只有**并行**检查（实测中位 19.36s）才回到 30s 内。分库实施必须同时改启动检查并发/跳过策略，否则不能解决启动门禁。
3. **设计 v1.35 已升版**：ADR-039 §D-039-5 的 D3/D4/D13/附录 C/§5 变更已由设计升版承接；实施由 M10-09/10/11 完成。
4. **保留清理性能**：产品 `select_retention_batch` 的 `ORDER BY rowid` 在 5 GiB 上退化为 TEMP B-TREE（O(N²)）；采样批 P95 4.89s，远高于 D3 <500ms。需独立任务优化（批选顺序、批量 DELETE、索引/分区）。
5. **物理文件不收缩**：保留只复用空闲页；5.22 GiB 高水位不会自动回到 <5 GiB。需 `VACUUM`/`auto_vacuum`/分库/重建，并纳入磁盘与备份预算。
6. **平台覆盖**：本机仅 Windows x64；macOS/Linux 未执行（`quick_check`/文件系统/磁盘差异可能改变绝对值，但 30s 阈值余量/并行收益需复测）。
7. **冷启动缓存限制**：未执行 OS 文件缓存清空；参考值为「生成/复制后首次检查」的冷-ish 值，Rust 真实 daemon 启动独立复核 86–127s。阈值越线幅度约 3–4×，缓存不足以改变结论。
8. **SQLite 实现差异**：压测子进程用 Node `node:sqlite` 3.51.2；产品 `rusqlite 0.41.1` bundled。真实 daemon 启动（§7）与子进程结果同量级，未发现实现差异导致的结论反转。
