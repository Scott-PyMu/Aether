## 1. 命令面契约登记（实现增量，非设计偏离）

### 1.1 `permissions_pending`（D9 待审批队列）

| 项 | 值 |
|---|---|
| 请求 | `{ session_id?: ULID }`（省略 = 全部会话；`deny_unknown_fields` + ULID 校验由 M1-08 框架承接） |
| 响应 | 数组（按 `requested_at` 升序 = 审批队列顺序）；无 pending 为 `[]`： |
| 条目 | `{ id, request_id, session_id, resource, action, target, canonical_target, requested_at, timeout_ms }` |
| 字段语义 | `target` = 原文（未规范化）；`canonical_target` = canonicalize 结果（重启恢复的票据为 `null`，UI 按原文展示）；`timeout_ms` = D9 审批超时（300000；`PermissionService::config().ask_timeout_ms`，不复制常量） |
| 未接线 | `core_not_ready`（不伪造空队列） |

### 1.2 `permission_resolve`（D9 用户决议）

| 项 | 值 |
|---|---|
| 请求 | `{ request_id: ULID, decision: "once" \| "session" \| "deny" }` |
| 映射 | `once` → allow + `PermissionScope::Once`；`session` → allow + Session；`deny` → deny（scope 无） |
| 响应 | `{ request_id, decision: "allow" \| "deny", scope, ticket_id }` |
| 非待审批 | `invalid_value` + 消息含稳定业务码 `permission_not_pending`（不新增 IPC 错误码枚举，口径同 `session_busy`） |
| 未接线 | `core_not_ready` |

断言链（「DoD1：待审批卡展示原文与规范化对照 → 允许（once）→ IPC 决议 + 事件收口」）：

1. `permissions_pending` 清单 → `permission-card`（`data-status=pending`、
   `data-request-id`）；
2. `permission-target-raw` = 原文 `D:\ws\a.txt`；`permission-target-canonical`
   同值且 `data-equal="true"` + 「规范化后一致」；不一致样本 `data-equal="false"` +
   「与原文不一致，请核对」（D9 评审 #10）；
3. `permission-timeout-note` 带 `data-remaining-ms`（>0）与 `data-expired=false`；
4. 点击 `permission-allow-once` → `resolvePermission(REQUEST_A, "once")`；
   点击 `permission-deny` → `...(..., "deny")`；
5. 决议后清单清空（`permission-card` 消失）；`permission.resolved` 事件收口为
   弱化结果态（`data-status=resolved`、「已允许（本次）」）；
6. 超时样本：deny 决议事件 `ts ≥ requested_at + 300000` → `data-status=timeout` +
   「已超时自动拒绝（300s）」；
7. 决议失败（`permission_not_pending`）→ `permission-error`（`data-code=invalid_value`）
   且自动刷新清单；
8. C6 边界声明渲染：「权限门仅约束经线协议上报的工具调用；适配器进程内行为不受此门约束」。

断言要点：

- **清单即 UI 数据源**：`permissions_pending` 返回原文 `target` 与 `canonical_target`、
  `timeout_ms=300000`、`requested_at`；决议前探针 `decisions=0`（决议只能来自 IPC 命令）；
- **允许/拒绝 → 适配器收到决议**：`permission_resolve(once)` → `permission.resolve`
  下发 → 适配器 `permission.resolved` + 工具终态；探针
  `requests_received == decisions == resolutions_sent == 1` 且
  `zero_passthrough=true`（100% 回环、零直通）；
- **超时 deny**：`ManualClock` +299.999s 不判超时；恰好 +300.000s 巡检摘除 → 清单移除
  + 适配器收到 deny + 审计 `permission.timeout`（DoD1「超时 deny 提示与审计可查」；
  提示 = UI `permission-timeout-note` / 「已超时自动拒绝（300s）」）；
- **M2-10 异常路径覆盖**（任务描述要求）：deny / 超时 deny / once / session 授权 /
  重启后 pending 决议（重复决议回 `permission_not_pending`）全部在 IPC 面重放通过。

## 4. 边界与偏离记录

1. **E2E 分层口径（与 M3-02 一致）**：DoD1 的「ask 弹窗 → 允许/拒绝 → 适配器收到决议」
   由两层共同证明——(a) 前端集成：真实 React/EventStore 驱动 `permission_resolve`
   调用参数（UI 面）；(b) Rust 集成：真实 Mock 适配器进程 + 真实网关，经
   `SessionBackend` 的**同一 IPC 命令实现**决议 → 适配器收到（命令层仅
   `parse_strict` 包装，M1-08 已有校验矩阵）。真实 WebView 内联回环 E2E 不可行：
   生产适配器注册随 M4-05 落地，当前注册表为空，无法在真实应用内产生真实 ask；
   不做「只渲染假 pending」的弱化 E2E（真实性优先）。
2. **权限服务生产装配基准目录**：策略引擎（`PolicyEngine`）需绑定工作区根；P0 工作区
   绑定（`workspace_set`/D14）随 **M3-08** 落地。本任务在绑定前以**数据目录**为基准
   目录（执行器权限网关仍为 `None`，M3-02 边界 9 不变——不产生回环请求），
   对既有语义无可观察影响；M3-08 接管工作区基准并接线执行器网关。
3. **超时判定口径（UI）**：`permission.resolved` payload 不携带 `timed_out`，UI 以
   「decision=deny 且决议时间 ≥ requested_at + timeout_ms」判 `data-status=timeout`；
   早于截止的用户 deny/取消保持 `resolved`。后端审计动作（`permission.timeout` vs
