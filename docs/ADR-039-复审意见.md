## 1. P0（阻断签核/实施）

### P0-1 `uiReadyAt` 定义与 S-00/写门互相冲突

**问题：**  
D-039-3 §1 定义 `uiReadyAt` 为“壳层可见 + 主界面可交互 + 首个 `health` 成功（取较晚者）”。但 D-039-3 §2 的启动检查表规定：`mode=startup` 时 UI 为 **S-00“正在校验数据（x/8）”**，写/新 run 被拒绝。S-00 是启动加载态，不是“主界面可交互”；在异常启动路径，首个 `health` 成功时 S-00 仍在显示，`uiReadyAt` 与“主界面可交互”不可能同时成立。

**依据：**  
D-039-3 §1 指标表；D-039-3 §2 状态表；UI-UX S-00（“启动加载态，窗口创建后 daemon 握手/健康未完成”）与 S-08（`storage_backpressure` 也映射到 S-08）。

**风险：**  
1.5s 验收无法定义：可以在用户仍看到 S-00 时判定“UI ready”，也可以在 S-00 不出现时判定“主界面可交互”；实现与 QA 会各自解释，G13 证据不可复现。

**建议：**  
二选一并写入 D-039-3/UI-UX：
- **方案 A（推荐）**：`uiReadyAt` = 壳层可见 + 首个 `health` 成功（不要求写可用）；另设 `mainInteractiveAt`/`writesEnabledAt`（检查完成后）。S-00 可保留；验收表分别列三个指标。
- **方案 B**：启动检查期间显示**主界面只读 + 校验横幅**（不显示 S-00），`uiReadyAt` 才可包含“主界面可交互”。若选 B，需改 UI-UX，不得复用 S-00。

### P0-2 `storage_backpressure` 写门与 D4/UI S-08 语义冲突

**问题：**  
D-039-3 §2 用 `storage_backpressure` + `detail.reason=storage_check` 拒绝检查期间的写/新 run。但：
- D4 的存储状态机只有 `normal` / `persist_degraded`，没有“检查中写门”这个第三状态；`storage_backpressure` 是队列 L2 背压的既有业务码，不是存储完整性状态。
- UI-UX S-08 的触发条件包含 L2 `storage_backpressure`；按现有 UI 规则，客户端可能显示 S-08 降级横幅，而 ADR 要求校验中显示 S-00、且“不是降级”。
- D4 规定 `health.storage_state` 是降级唯一事实源；现在写门由错误码而非 `storage_check`/`storage_state` 表达，存在双事实源。

**依据：**  
D-039-3 §2 状态表与“检查中写门复用 `storage_backpressure`”段；《设计文档》D4 存储降级状态机；UI-UX S-08 触发条件；`packages/protocol/src/error_codes.json` 的 `storage_backpressure`。

**风险：**  
UI 显示错误状态（S-08 而非 S-00）、客户端把校验中当降级、D4 单一口径被破坏；如果安全/QA 不接受，ADR 又留下“另立 ADR”的未决口子，v0.2 不能签核。

**建议：**  
- 在 D4 明确定义“检查中写门”为**独立于降级的启动阶段**（如 `storage_check.write_gate=checking` 或 `storage_state=normal` + `write_gate=checking`），并规定所有写命令返回的 `business_code`/`detail` 与 UI 映射。
- UI 选择 S-00/S-08 时以 `health.storage_check.state` 优先，不以 `storage_backpressure` 单独判定。
- 删除“若安全/QA 认为不可接受再另立 ADR”的条件句；在 v0.3 直接定稿，否则该条不能作为冻结契约。

### P0-3 跨库导入/会话删除的原子性未设计

**问题：**  
v0.2 只写了两句“结果”，没有设计：
- D-039-1 §6：会话删除“先按 `sessions.shard_id` 删除该片 `events`，再删除主库 `sessions`/`messages`/`runs`；跨库不是单事务，必须记录部分失败并重试/报错，不得留下孤儿事件。”
- D-039-5 §2：导入 session 写入 `shard_id`、事件按会话路由；失败/回滚“同时覆盖主库与分片”。

但 ADR-034 的导入是**单 staging DB + 原子切换**；分库后是主库 + 8 分片（+ manifest）的**多库 staging/切换**。先删 events 再删主库，如果主库删除失败，会留下“无事件的会话”；先删主库再删 events，会留下孤儿事件。两种顺序都需要 tombstone/重试/补偿，v0.2 未定义。

**依据：**  
D-039-1 §6；D-039-5 §2；ADR-034 维护窗口/staging/原子切换；《设计文档》D13 导入维护例外。

**风险：**  
删除半成功导致会话历史缺失；导入半成功导致主库/分片不一致；重试可能重复删除/重复导入；数据不可恢复。

**建议：**  
在 v0.3 增加“跨库维护协议”：
- **会话删除**：先写 `session_deletion_pending`/tombstone（主库事务），再删分片 events，再删主库行，最后清 tombstone；任一步失败可重试，启动清理 pending；禁止先删主库导致孤儿事件，或先删 events 后主库失败导致空会话。
- **导入**：staging 必须包含主库 + 分片事件 + manifest；完成校验后整套原子切换（目录 generation/pointer）；失败整套回滚；导入与备份/恢复/清理互斥。
- 如果 v0.3 无法闭合，明确“M10-09 暂不支持导入/会话删除跨库”，并在 M10-04/M10-09 证据中登记限制；不得用一句“失败/回滚同时覆盖”代替设计。

### P0-4 `backup_list`/`backup_restore` 契约未冻结

**问题：**  
D-039-5 §3/§4 把备份从“单文件”改为“整套目录 + manifest”，`backup_list` 按套列出、`backup_restore` 按套恢复，且“开发阶段旧单文件 `.db` 备份不再作为恢复输入”；但同一段又写“参数/响应语义在 M10-09 证据中固定，必要时重录 M9-01”。ADR 声称“冻结契约”，却把 `backup_list`/`backup_restore` 的 DTO/响应语义留给实施证据，属于契约未冻结。

**依据：**  
D-039-5 §3/§4；《设计文档》D7 `backup_list`/`backup_restore`；AGENTS §2.8（生成物/契约）；M9-01 baseline。

**风险：**  
UI/客户端在实现时才知道返回结构；生成物/M9-01 重录范围不清；`backup_restore` 的 `source` 从文件变目录是破坏性变更，可能破坏既有命令契约和测试。

**建议：**  
在 v0.3 冻结：
- `backup_list` 响应：套 id/路径/时间/大小/分片数/状态/校验；是否兼容旧字段。
- `backup_restore` 请求：`source` 类型（内部套 id / 外部目录 / manifest 路径）、是否保留旧 `.db` 兼容（开发阶段可拒绝，但要在契约中写明）。
- `backup_create` 是否需要新参数/返回套 id；不新增命令，但响应字段变更需登记。
- M9-01 重录范围、生成物 diff、UI 适配；写入 D7/附录 C/§6.1。

## 2. P1（高风险，需 v0.3 修订）

### P1-1 `initialize` 2s 目标与 `uiReadyAt` 1.5s 硬预算冲突

**问题：**  
D-039-3 §1 保留 `initialize` 的“目标 2s / 硬超时 10s”，同时要求 `uiReadyAt` ≤1.5s。`uiReadyAt` 包含 `initialize`；如果 `initialize` 在 1.5–2s 完成，既满足既有目标，又不满足 ADR 的 1.5s。D-039-3 只说“不是放宽理由”，没有把两个预算对齐。

**依据：**  
D-039-3 §1；《设计文档》D2 启动序列（`initialize` 目标 2s/硬超时 10s）；P2 计划性能矩阵。

**风险：**  
实现/QA 对“1.5s 是否包含 initialize”理解不一致；M10-10 可能因 initialize 1.6s 被判失败，但既有设计仍认为合格。

**建议：**  
在 v0.3 明确预算分解：`initialize` 目标 ≤1.5s（5.22GiB 启动路径）或把 `uiReadyAt` 定义为“initialize 完成后 + 首个 health”，并同步修改设计/P2 性能矩阵；若无法做到，按 AGENTS §7 报告，不得同时保留 2s 和 1.5s 两个硬目标。

### P1-2 §5 把未越线指标说成“单库瓶颈”

**问题：**  
§5 否决“仅启动优化”的理由写：“备份 163.85s/恢复 82.26s/补读 95.7ms 均指向单库容量/IO 瓶颈”。但 ADR-038 的阈值是备份 ≤600s、恢复 ≤900s、补读 <150ms，这三项在 M10-08 判定表中都是**通过**；唯一的硬触发是 `quick_check` >30s。把它们说成“瓶颈”会与 ADR-038 判定表冲突。

**依据：**  
ADR-038 D-038-2 阈值；M10-08 证据 §6 判定表；ADR-039 §5。

**风险：**  
评审/审计认为决策理由与数据不一致；把“改善项”误当“越线项”，可能扩大分库理由。

**建议：**  
改写为“分库的**支持性收益**（备份/恢复/补读改善），不是 ADR-038 的硬触发；硬触发仍是 `quick_check` >30s；物理高水位是独立容量风险”。保留 A 的用户裁定，不改变结论。

### P1-3 整套恢复的原子切换未定义

**问题：**  
D-039-5 §4 写“当前整套库改名 `.pre-restore-<ts>`；复制新整套（跨盘临时文件 + 原子 rename）”。恢复对象是主库 + 8 分片 + `shards.json` + manifest 的**多文件集合**；跨盘 `rename` 不是原子操作，逐文件 rename 也可能留下半套。v0.2 没有定义 generation 目录/指针、同卷暂存、fsync 顺序或失败回滚粒度。

**依据：**  
D-039-5 §4；《设计文档》D13 七步恢复（单库）；D-039-5 §3 备份套。

**风险：**  
恢复中断后主库/分片版本不一致；启动 fail-closed 拒绝，用户无法恢复；`.pre-restore` 与半套新库混杂。

**建议：**  
v0.3 定义：在数据目录同卷创建 generation 目录（或 `.restore-staging`），完整复制 + fsync + manifest 校验后，以目录 rename 或指针文件原子切换；`.pre-restore` 保留整套；任何一步失败整套回滚；加入恢复中断故障注入。

### P1-4 主库 `events` 非空/分片缺失的启动错误映射未定义

**问题：**  
D-039-1 §1 规定主库 `events` 非空 → 拒绝启动（S-12；复用 `IpcErrorCode::Internal`，`code=internal`，`detail.reason=main_events_nonempty`）；D-039-6 对分片缺失建议用 `business_code=db_open_failed`。但 UI S-12 的 `ShellFatalReason` 只有 `daemon_start_failed/handshake_failed/a4_blocked/db_open_failed/schema_checksum_mismatch/data_dir_locked`，没有 `internal`；`IpcErrorCode::Internal` 也不等同 S-12。v0.2 未定义退出码/首帧 error/S-12 reason 的映射。

**依据：**  
D-039-1 §1；D-039-6；《设计文档》D2/D7 启动致命错误；`apps/desktop/electron/startup.ts` 的 `ShellFatalReason`；M9-03 启动错误证据。

**风险：**  
主库 events 非空时 daemon 返回 generic `internal`，UI 无法映射 S-12，用户只看到通用错误；M9-03/M9-01 测试无法断言；分片缺失与 `db_open_failed` 语义混淆。

**建议：**  
v0.3 为每个启动不变量列一张表：条件 → `IpcErrorCode`/`business_code`/退出码/S-12 `data-reason`/UI 文案。建议：
- 主库 events 非空 → `db_open_failed` 或新增已登记 reason（若新增，走 D7/ADR 计数）；
- 分片缺失/损坏 → `db_open_failed`；
- `shard_id` 越界/为空 → `schema_checksum_mismatch` 或 `db_open_failed`（二选一并固定）。
不得只写 `internal` + `detail.reason` 而声称 S-12。
