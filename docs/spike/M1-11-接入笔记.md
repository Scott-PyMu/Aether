## 鉴权

### Codex
- 登录态在 `CODEX_HOME`（默认 `~/.codex`）：`auth.json` + `config.toml`；`codex login status` 可查。
- 非交互注入：`printenv OPENAI_API_KEY | codex login --with-api-key`（stdin 传入，不落命令行历史）。
- 自定义 provider（本次实测的非官方端点场景）在 `config.toml` 配置：
  `model_provider` + `[model_providers.*]`（`base_url` / `wire_api = "responses"` / `env_key`）。
- 红线：脚本只读环境变量，不读取/写入用户 `auth.json`；证据文件经 `redact()` 过滤密钥。

### Claude Code
- 鉴权经 `--settings <临时文件>` 注入（`env` 字段）：
  `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`（Bearer）+ `ANTHROPIC_MODEL` +
  `ANTHROPIC_DEFAULT_{HAIKU,SONNET,OPUS}_MODEL`（避免 alias 回落到中转不支持的模型）。
- 实测：同一端点 `x-api-key` 返回 401，**必须走 `Authorization: Bearer`**（即 `ANTHROPIC_AUTH_TOKEN`）。
- `--setting-sources local --settings <file>` 用于隔离用户级 settings（本机存在指向失效本地代理的残留配置，
  见「已知坑 1」）。临时 settings 文件写入 OS 临时目录，run 结束后删除，不落仓库。
- 本机 OAuth/keychain 登录态不可用（`--setting-sources` 排除用户配置后报 Not logged in），
  故 spike 统一走 token 模式；M2-02 需在 UI 侧提供同样的 token 注入路径（对应 D10）。

### DeepSeek Harness
- 配置位于 `DSH_HOME`（默认 `~/.dsh`）：`settings.yaml`（provider/model，如 `llm-pi-ai.providers.<name>.apiKeyEnv`
  指向环境变量、`api: openai-completions`、`baseURL`）+ `.credentials.yaml`（`refs:` 直接映射 env 名到密钥）。
- 非交互注入：provider 的 `apiKeyEnv` 直接读环境变量，密钥不写入 settings；CI 步骤按该格式生成临时 settings。
- headless profile 无 `--model` 等模型开关（模型由 settings 的 `agent-default-model` 决定），
  因此 CI/本地要切换模型只能改 settings 或 `--patch` overlay。
- **ACP 路线（0.1.5-rc.2）**：隔离安装 `@deepseek-ai/dsh@0.1.5-rc.2`（自带 `dsh-acp-app`），
  用 `DSH_HOME=<隔离目录>` + `--profile acp --patch <overlay>` 启动；overlay 只需覆写 `acp` 行的
  `provider/model`（provider 定义来自复制进隔离 home 的 settings.yaml）。密钥通过隔离 home 的
  `.credentials.yaml`（0600，仅本机）或 env 注入，仓库与证据不落密钥。

## 会话模型映射

| Aether 概念 | Codex | Claude Code | DeepSeek Harness |
|---|---|---|---|
| 创建会话 | `codex exec --json`；会话 id 来自首行 `thread.started.thread_id` | `claude --session-id <uuid> -p ...`（客户端预生成 UUID） | `dsh --profile headless <task>`；会话 id 由内部生成（`session-<uuid>`）且不外显 |
| 续会话 | `codex exec resume <thread_id> ... -` | `claude --resume <session_id> -p ...` | ❌ headless 无 `--resume`/`--session-id`（web/TUI profile 有 `--resume`，但非本次范围） |
| 会话 id 出现位置 | `thread.started.thread_id`（仅出现一次） | 所有事件的顶层 `session_id` | 不出现（仅落盘 `$DSH_HOME/sessions/**/session.jsonl.zstd`） |
| 首次 id 是否可预生成 | 否（服务端生成，需回写持久化） | 是（`--session-id` 显式指定） | 否（不可指定） |
| 实测续聊 | 通过：第 2 轮 `exec resume` 命中第 1 轮记忆（回复 `AETHER-SPIKE-41`；隔离/非隔离配置各验证 1 次） | 通过：`--session-id` → `--resume` 命中记忆（回复 `AETHER-SPIKE-41`） | 不适用（headless 无续聊；已验证会话文件落盘） |
| 无状态提示 | 会话文件在 `CODEX_HOME/sessions/**`；`--ephemeral` 可禁用落盘 | 会话记录在 `~/.claude/projects/**`；`--no-session-persistence` 可禁用 | 会话文件 zstd 压缩、任务结束后 flush 落盘；无法边跑边读 |

对 M2-02 的含义：Aether 侧需要持久化 `runtime_session_id`（Codex 只能回写，Claude 可预生成）；
run 与 session 解耦，run 级 id 由 Aether 生成，不依赖 CLI。DSH headless 不满足会话模型映射要求。

DSH 官方 ACP（0.1.5-rc.2）补充：
- `session/new`（返回服务端生成 `sessionId` + `configOptions`，model 选项的 `currentValue` 为
  `["<provider>","<model>"]`）→ `session/prompt`（ACP 请求，settle 时返回 `stopReason`）→ `session/close`；
- `session/resume {sessionId, cwd, mcpServers}` 支持跨进程恢复（实测第 2 个进程命中第 1 轮记忆）；
- `session/list` 可分页列持久会话；`session/cancel` 为协议级取消（见「中断机制」）；
- 会话落盘在 `DSH_HOME/sessions/**`（JSONL）；Aether 的 `runtime_session_id` 可直接取 ACP `sessionId`。

## 权限映射

设计边界（设计文档 §2.1 安全边界声明 / 评审修订 #1）：**适配器进程内行为不经 D9 权限门**，
CLI 自身的沙箱/审批只作为启动配置（信任级），不构成 Aether 的审批回环。

| 能力 | Codex | Claude Code | DeepSeek Harness |
|---|---|---|---|
| 文件/命令沙箱 | `--sandbox read-only / workspace-write / danger-full-access` | `--permission-mode default/acceptEdits/bypassPermissions/plan/dontAsk/auto` | 插件体系（`dsh-sandbox-local` / `dsh-sandbox-windows-acl` / `dsh-permission-presets`），headless 走 settings 默认，未在本次 spike 调参 |
| 审批策略 | `approval_policy` / `approvals_reviewer`（config.toml） | `--allowedTools` / `--disallowedTools` / settings.permissions | `dsh-permission-presets` + `dsh-user-approval`（面向交互式 profile；headless 一次性模式未实测审批回环） |
| 全放行（自动化） | `--dangerously-bypass-approvals-and-sandbox` | `--dangerously-skip-permissions`（root 下需改用 `--permission-mode auto`） | 通过 preset/settings 配置（无 CLI 全放行开关） |
| 非交互下的工具事件 | `item.started/completed`（`command_execution` / `mcp_tool_call` / `file_change`） | `assistant.message.content[].tool_use` + `user.tool_result` | headless 无事件输出（终稿 only）；工具经 session 事件落盘，无法实时上报 |
| 审批回环 | exec 模式无交互审批通道 | print 模式无交互审批通道；SDK 另有 `canUseTool`/hooks 机制，不在本次 spike 范围 | 交互式 profile 有 user-approval 插件；headless 不可用 |

对 M2-02/M2-03 的含义：MVP 的权限门只约束**经线协议上报**的工具调用；CLI 内部的
shell/文件行为按信任级放行（比如 `--sandbox workspace-write` + 预授权），必须在接入笔记与
审计字段中明示边界；若后续要拦截到 CLI 进程内行为，需要走 CLI 的预授权/沙箱配置或 P3 沙箱。

## 流式事件模型（实测）

### Claude Code：`-p --output-format stream-json --include-partial-messages --verbose`
- 逐 token 文本：`stream_event` → `content_block_delta` (`text_delta`)，可直接拼接；`thinking_delta` 为推理，不入正文。
- 快照：`assistant`（最终 message，含 `tool_use`）；终态：`result`（`is_error`/`subtype`/`usage`/`duration_api_ms`）。
- 结论：文本级流式可用，可直接映射 Aether `message.delta` 类事件。

### Codex：`codex exec --json`
- 事件：`thread.started` / `turn.started` / `item.started|updated|completed` / `turn.completed|failed` / `error`。
- **实测本版本（0.145.0）+ 本中转下无文本 delta**：`item.updated` 未出现，正文只在
  `item.completed(item.type=agent_message, text=...)` 整段到达；同时 codex-core 会记录
  `OutputTextDelta without active item` 告警（中转流事件顺序差异）。
- 结论：事件级流式可用（工具/推理条目可逐条上报），但**正文流式为整段**；M2-02 若选 Codex，
  需在接入层自行做增量呈现策略（如整段落地 + 打字机效果不属于协议层）。

### DeepSeek Harness：`dsh --profile headless <task>`（0.1.1-rc.2）
- **无流式事件**：headless 驱动在任务结束后一次性打印最终 assistant 文本（源码
  `@deepseek-ai/dsh-headless/lib/index.js` 的 `summarize()` 仅从 session events 聚合最终消息），
  stdout 无 JSONL/增量事件；实测 20 次 run 均为单 chunk 终稿。
- 终态：进程退出码（0=completed / 1=failed），错误经 stderr `dsh: <code>: <message>`。

### DeepSeek Harness：官方 ACP（`--profile acp`，0.1.5-rc.2）
- JSON-RPC 2.0 over stdio；进程 stdout 只承载协议（日志走 stderr）。
- `session/update` 语义更新：`agent_message_chunk`（assistant 正文，**committed 整段**）、
  `agent_thought_chunk`（推理）、`tool_call` / `tool_call_update`（工具生命周期）、
  `usage_update`（上下文占用 `used/size`，非输出 token）。
- **实测无 token 级 delta**：确定性提示词 20/20 次、以及 2195 字符长回答，`agent_message_chunk` 均恰好 1 个；
  官方 README 明示 "raw provider deltas … stay off the wire"，属协议设计而非 bug。
- 结论：**语义更新级**流式可用（早于 prompt settle 到达、工具/推理可逐条上报），但正文粒度=整段；
  与 Codex 本环境的情况同类，不满足 A1 的逐 token 流式期望。hermes-studio 为拿到 token 级 delta
  注入私有 Cordis 插件（`agent/assistant-stream` → 自定义 ACP 通知），属适配器实现，超出最小 spike。

### DSH 适配器增强可行性（已实验验证，供 M2-02 之后的专项任务参考）
- 实验：自研 ~10 行 Cordis 插件（不拷贝 hermes 代码），仅通过 `--patch` overlay 的 `insert` 行注入
  （插件包放 profile 的 `node_modules`，不修改 DSH 源码），订阅 `ctx.on('agent/assistant-stream')`：
  实测收到 `type=chunk, chunkType=text-delta` 的**原始 provider 增量**（单帧 3–16 字符，随生成逐帧到达），
  另有 `start`/`end` 帧与 `attemptId` 可用于归并。**结论：token 级 delta 通道可行且无需 patch DSH 源码。**
- 与 hermes 的差异：hermes 需要 patch `@deepseek-ai/dsh-acp` 的源码接缝，是为了把 delta 塞进 ACP 标准通知
  （单通道、顺序严格）；Aether 的适配器本身就是 ACP 客户端，可走**双通道**：官方 ACP 负责权威 session/终态，
  插件经带外通道（session 级 sidecar 文件/命名管道/本地 socket）送 delta，客户端按消息做前缀消费去重。
  两条路线都能与 hermes 行为一致，双通道维护成本更低。
- 版本门闩（必须）：pin DSH 版本（本 spike 实测 0.1.5-rc.2；0.1.1-rc.2 无 acp）+ 启动探针校验
  `agent/assistant-stream` 帧形状，不匹配即拒绝加载（与 D6 协议 major 校验同思路）。
- 合规：只参考 hermes 的公开行为与 DSH 包内公开契约，不拷贝其代码；使用 DSH 内部事件契约的维护风险
  需在对应任务证据/ADR 中留痕（A11 净室合规）。

## 中断机制（DoD2 ③）

- 三个 CLI 均为一次性进程，中断 = 进程信号 / 进程树回收：
  - Windows：`taskkill /PID <pid> /T /F`（必须 `/T` 回收整树，CLI 会拉起子进程/MCP）；
  - POSIX：进程组 `SIGINT`（spawn 时 `detached: true`）。
- 实测（Claude/Codex：首 delta 后 500ms、无首 token 时 8s 兜底；DSH headless：固定 2500ms；数值为「发起中断 → 进程关闭」）：
  - Claude Code：**399ms**；中断时已收到正文 170 字符（7 个 text delta），exit code 1；
  - Codex：**394ms**；中断发生在 `thread.started`/`turn.started` 后、正文到达前（本环境正文整段到达）；
  - DeepSeek Harness（headless）：**342ms**；中断发生在终稿输出前（无部分文本，符合 headless 无流式特性），exit code 1；
  - DeepSeek Harness（ACP）：**9ms**，走协议级 `session/cancel` → prompt settle 返回 `stopReason: "cancelled"`
    （无需进程强杀；进程随后正常 close）。这是四个候选里最干净的中断路径。
- 对 M2-01/M2-05 的含义：interrupt 走「进程树级回收」路径，与 D5 一致；CLI 无协议级取消消息，
  run 终态由适配器在 kill 后合成 `run.failed(interrupted)`。DSH ACP 是例外：有协议级取消，
  M2-02 若选 DSH 可直接映射为 `session/cancel`（仍建议保留 kill 兜底）。

| Claude Code | ① 同 run 官方聚合结果 `result.result`（主基线，逐 run）；② 官方非流式调用 `claude -p --output-format json` 的 `result`（交叉基线，每轮 spike 前置一次） | `normalize(拼接 text_delta) == normalize(result.result)`；且 `normalize(result.result) == normalize(control.result)` |

| DeepSeek Harness（ACP） | ACP 首次运行输出为 control（协议只发 committed 文本）；20 次 run 均与 control 比对 | `normalize(agent_message_chunk 拼接) == normalize(control 文本)` |

- `normalize` 规则：统一换行、去行尾空白、去首尾空白（不改变正文语义）。
- 基线原始值与获取时间记录在 `scripts/test/.tmp/m1-11/baseline.json`（gitignored，CI artifact）。

  - Claude Code：run 内基线 **20/20** 一致；交叉基线（非流式 control）**20/20** 一致；

    control 基线本身成功产出（见 `summary.json.candidates.codex.control`）。

  - DeepSeek Harness（ACP）：control **成功**，20 次 run 基线 **20/20** 一致（run 数 20/20 完成）。

## 已知坑

1. **本机 cc-switch 残留**：`~/.claude/settings.json` 曾接管为本地代理 `http://127.0.0.1:15721`，
   而该代理进程未运行（连接拒绝 → CLI 空转重试 10 次）。spike 用 `--setting-sources local --settings`
   绕过；M2-02 若复用用户级配置，必须检测「死代理/失效凭证」并给出明确错误。
2. **Claude Code 的 base_url 不能带 `/v1`**：CLI 会自行追加 `/v1/messages`，带 `/v1` 会拼成
   `/v1/v1/messages` 并伪装成「模型不存在」（`api_error_status: 404`，实际是路径错误）。
3. **鉴权头差异**：同一中转端点 `x-api-key` 401、`Authorization: Bearer` 200；统一使用
   `ANTHROPIC_AUTH_TOKEN`（Bearer）并在接入笔记记录，避免 M2-02 踩坑。
4. **Codex 正文无流式 delta（0.145.0 + 本中转）**：见「流式事件模型」；codex-core 会打
   `OutputTextDelta without active item`，但 `turn.completed` 正常。对 UI 流式呈现是实质约束。
5. **Codex 中转（Responses 流）间歇性损坏**：定向探测 `POST /responses {stream:true}` 连续 4 次，
   2 次在 20s 内只收到 2 个事件/174B 或 20 个事件/47.5KB 但缺 `response.completed`（超时失败），
   另 2 次 2.9–7.2s 正常完成；非流式请求始终正常。20 次样本中 1 次 503、5 次重连耗尽失败、
   1 次 240s 挂起（不同轮次分布不同）。**终态判定必须等进程 close/turn.completed/turn.failed**，
   不能见 `error` 即判失败（与 hermes-studio 的「终态仲裁」经验一致），同时必须设置挂起超时。
6. **模型不受支持时表现为「静默拖长」**：本机默认 config 的模型在中转不可用，`codex exec` 会空转到超时；
   必须显式 `-m`（spike 默认 `gpt-5.5`）。Claude 侧同理需显式 `--model`。
7. **Windows CLI 是 .cmd/.ps1 shim**：直接 spawn `codex`/`claude` 会经过 cmd 二次解析（引号/长中文风险）。
   spike 改为解析 npm 包入口直连（`node codex.js`、`claude.exe`）；保底路径才用 `cmd.exe /d /s /c`。
   注意 `codex exec resume` 不接受 `--sandbox`（需 `-c sandbox_mode=...`），`--cd` 也仅存在于 `exec`。
8. **进程树回收**：两个 CLI 都可能拉起子进程；必须 `taskkill /T`（Windows）/ 进程组 SIGINT（POSIX），
   与 D5 一致。裸杀单 PID 会留孤儿（AGENTS §2.5）。
9. **MCP/用户配置污染对 Codex 是量级问题**：本机用户级 `CODEX_HOME` 带 MCP 工具定义，使
   单次请求输入约 3.3–3.9 万 tokens、单 run 20–120s、失败率显著升高；隔离 `CODEX_HOME` 后
   输入与延迟大幅下降（首 token p50 11.6s），失败率降到 1/20。**CI 必须用独立 CODEX_HOME**；
   Claude 侧必须 `--strict-mcp-config` + `--setting-sources local`。
10. **thinking 块兼容**：本中转返回 `thinking` 内容块；正文拼接只取 `text_delta`，基线与正文一致
    （hermes-studio 亦记录了中转对加密 thinking 的兼容重试，M2-02 需关注）。
11. **`--tools ""`（Claude）**：spike 关闭全部工具以消除审批与副作用；M2-02 联调工具调用后需重新评估
    延迟与事件量。Codex 用 `--sandbox read-only` 达到同等效果。
12. **opt-in CI job 未在 GitHub runner 上执行**：`.github/workflows/spike-m1-11.yml` 只允许手动触发，
    需要仓库 Secret；本机以同一脚本重复执行（多轮、含隔离配置）作为「可重复执行」证据；
    CI job 本身标注为未运行，待密钥配置后首次手动触发。
13. **DSH 的流式/会话能力只在非 headless profile**：`headless` 是官方一次性驱动（终稿 + 退出码，
    无增量事件、无 `--resume`）；`web` profile 虽有 `/api`（HTTP unary + `events.mux`/`events.host`
    下行 WebSocket），但 README 明确其为浏览器载体：browser-trust fence（Host/Origin 校验、非鉴权）、
    Typert RPC 生成契约、无认证层，Drive-by 远程访问被刻意不支持。故 DSH 的流式接入不属于最小 spike，
    需单独立项（A1 降级路径 2：TUI PTY 或 web-API 桥）。
14. **DSH profile 依赖需先安装**：profile 由 `dsh.profile.bundles` 组合（如 `@deepseek-ai/dsh-base` +
    `@deepseek-ai/dsh-headless`），干净机器需先 `dsh plugin --profile headless add @deepseek-ai/dsh-headless`
    （或等价 pnpm 安装）；会话文件为 zstd 压缩、任务结束后 flush，无法边跑边读（不能用作流式旁路）。
15. **DSH 无 usage 输出**：headless stdout 只有文本，无 token/成本数据；ACP 只给上下文占用
    （`usage_update.used/size`），无输出 token；吞吐基线只能记录端到端耗时，
    M2-02 若接入需从会话文件或自身计时补充计量。
16. **DSH ACP 只在 0.1.5+**：本机全局是 0.1.1-rc.2（只有 headless/web），ACP 需 `@deepseek-ai/dsh@0.1.5-rc.2`
    （自带 `dsh-acp-app`；`--profile acp` 由 app-boot 模板自动初始化）。本 spike 隔离安装到临时目录，
    用户全局 DSH 未改动；如升级用户级 DSH 需重新验证 web/headless 现有用法。
17. **ACP 的 profile/模型注入**：`acp` 行默认 `provider: deepseek-official`，必须用 `--patch` overlay
    覆写 `acp` 行（`provider/model`）；provider 的 baseURL/apiKey 来自 `settings.yaml` 的 `llm-pi-ai`
    与 `.credentials.yaml` 的 `refs`（env 名 → 密钥）。改动只发生在隔离 `DSH_HOME`，不触碰用户配置。
18. **ACP 生命周期细节**：server 在 stdin EOF 时退出（`exitOnStdinEnd`），正常收尾需
    `session/close` → `stdin.end()`；`session/prompt` settle 才代表 run 终态（`stopReason`），
    不要在收到第一条 `session/update` 时提前判定完成；`session/request_permission` 是 server→client
    的请求，客户端必须应答（spike 自动允许；M2-02 需按「权限映射」节的 D9 边界映射为预授权策略）。
19. **DSH 插件注入的两个硬要求**（适配器增强实验发现）：① 插件包名从「dsh 安装域」或「profile 目录的
    node_modules」解析，放 `profiles/node_modules`（共享 fallback）无效——首次实验即因此加载失败；
    ② 插件 `package.json` 必须是**无 BOM** 的 UTF-8，Windows PowerShell 5.1 `Set-Content -Encoding utf8`
    会加 BOM，导致 `dsh-typert-loader` 直接崩溃（`Unexpected token '﻿'`）。CI/脚本一律用 Node/Python
    写 JSON，或显式去 BOM。

## 对 M2-02 的结论

- **选定适配器：Claude Code**（M2-02 的 `runtime_id = claude-code`）。
- 线协议映射（依据本笔记「会话模型映射」「流式事件模型」「权限映射」）：
  - `createSession` → `claude --setting-sources local --settings <scoped> --strict-mcp-config -p
    --output-format stream-json --include-partial-messages --verbose`，首轮 `--session-id <uuid>`；
  - `sendMessage` → stdin 写入 prompt；`content_block_delta/text_delta` → 文本 delta 事件；
    `result` → run 终态（`is_error`/`subtype`/`usage`）；
  - `interrupt` → 进程树回收（`taskkill /T /F` | 进程组 SIGINT），终态由适配器合成；
  - 鉴权 → `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`（Bearer）+ `ANTHROPIC_MODEL`，经 OS Keychain
    引用（D10），密钥不进 CLI 用户级配置（参考本 spike 的隔离 settings 注入）。
- 风险与待办：
  1. 上游端点稳定性决定 run 完成率（本 spike 的 Claude 端点 20/20 稳定；仍需 M2-02 一致性测试覆盖异常路径）；
  2. 工具调用/审批：Claude 在 print 模式下无交互审批通道，M2-02 需明确「CLI 预授权/拒绝 + 事件上报」策略，
     并在 M2-03 记录与 D9 的边界（适配器进程内行为不经权限门）；
  3. thinking 块与中转兼容性（参考 hermes-studio 的加密 thinking 重试经验），M2-02 需在异常路径测试中覆盖；
  4. Codex 适配器若在 P1 启用：需先满足「稳定端点 + 20/20 复测」，并解决正文整段到达的 UI 流式问题；
  5. DSH 本轮评估为部分通过：官方 ACP 的会话/恢复/协议取消可用，但无 token 级 delta；
     已实验验证「自研 Cordis 插件经 `--patch` 注入即可拿到原始 delta」（见「DSH 适配器增强可行性」），
     若后续需要第二/第三适配器，可按该方案做专项（插件 + 双通道去重 + 版本探针 + 20 次回归），
     并用 `deepseek-harness-acp-spike.mjs` 复测。
