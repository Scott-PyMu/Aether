## 0. 评审方法

按 `评审要求.md` 的五步执行：

1. **需求是否明确**：ADR-040 是否明确了优化目标、禁止范围和残余风险接受口径；
2. **设计是否覆盖**：是否覆盖主库/分片、干净/异常启动、后台/周期检查、`health`/UI、sidecar 生命周期；
3. **开发是否可执行**：是否有唯一实现计划、任务 ID、修改/禁止修改范围、与现有代码的差异；
4. **验证是否可证明**：是否有可复跑测试、真实数据、故障注入和未验证项说明；
5. **风险是否可控制**：是否有失效条件、回退触发器和安全/QA 签核。

结论：**第 1、3、4、5 步均未闭环；第 2 步存在主库/后台检查的覆盖缺口。** 产品已确认范围与 UX 方向，但 ADR 文本尚未落实这些裁定。

## 1. 总体结论

### 1.1 文档完整性

**不足。** ADR-040 只有 48 行，包含背景、决策、安全论证、验证、后续五节；缺少：

- 与 ADR-039 v1.0 的**取代/修订关系**（是修改 D-039-2 第 2 项，还是新增例外？）；
- **失效条件/回退触发器**（什么情况下必须退回 ADR-039 全量检查）；
- **任务 ID/实施范围/证据清单**（M10-10 已按 ADR-039 执行完毕，产品已确认 ADR-040 需在 G13 前实施，但 ADR 没有新任务编号）；
- **产品/安全/QA 签核项**（特别是未检查分片的残余风险）；
- **`health`/UI/验收指标的语义变化**（`checked_shards/total_shards`、`storageCheckCompletedAt`、后台全量检查保留）。

### 1.2 一致性状态

**不一致。** ADR-040 的决策与已签署的 ADR-039 v1.0 存在直接差异：

- ADR-039 D-039-2 第 2 项原文：**「任一不匹配（含 WAL 非 0/缺失但 size 变化、manifest/分片缺失、文件头变化、版本升级）→ 全量并行检查。」**
- ADR-040 §2 第 2 项：**「启动时仅对指纹变化的分片执行 `quick_check`；出现任一脏分片时附带检查主库。」**

这不是措辞差异，而是**启动检查范围/写门/证据口径的变更**。ADR-040 必须明确写成「修订 ADR-039 D-039-2 第 2 项」，并同步设计 v1.35、P2 v0.14、UI-UX v0.20 和 M10-10 证据口径；不能仅以「实现优化」名义绕过设计变更流程。

产品 2026-11-17 已裁定 **G13 前实施并纳入 M10-10 补充证据**，但 ADR 头部/§5 仍写「本 ADR 不进入实现/G13 判定」「G13 以 ADR-039 字面与 M10-10 证据为准」。**该文本与产品裁定直接冲突**，是本次评审新增的 P0（P0-4）。

### 1.3 最大风险

1. **G13 范围冲突**：产品已定 G13 前实施，但 ADR 声明不进入 G13；没有新任务 ID、没有重开 M10-10 证据/G13 条件的计划。若按现文执行，G13 证据与实现行为不一致。
2. **数据完整性漏检**：主库单独变脏（`messages`/`runs`/`audit_log`）时，按 ADR-040 字面不会触发主库 `quick_check`；干净指纹但页级损坏的分片在写门打开后仍可被写入，直到后台/周期检查发现。
3. **验证不可证明**：当前代码 `plan_startup_checks` 是 ADR-039 全量回退，测试明确断言「脏分片 → 主库 + 全部分片」；ADR-040 §4 却引用「仅该分片进入计划」和 15.78/15.93s，二者与仓库现状相反。选择性检查在仓库中曾实现（`8b76410`）后又被回退（`11cb438`），当前没有可复跑的 selective 证据。
4. **后台/周期检查兜底不成立**：产品已确认保留 ADR-039 的干净启动后台全量 `quick_check`，但 ADR 没有写明；也没有定义选择性检查通过后 `background_check_completed`/`clean_start_count` 如何写回 sidecar。若把「只检查了脏分片」记为「后台检查完成」，下一次启动可能错误地严格跳过。
5. **残余风险签核未完成**：产品 Q4 已接受残余风险，但 ADR-039 D-039-2 要求「必须写入证据并由安全/QA 签核接受」；ADR-040 仍未提供风险段落、最大暴露窗口和「干净指纹 + 页级损坏」故障注入。

### 1.4 安全专项

未发现「把权限控制误述为沙箱」的问题；ADR-040 不新增外部信任边界、命令面、事件类型、设置键或第三方依赖。但本 ADR 改变的是**完整性检查的 fail-closed 边界**，属于安全/数据完整性相关决策，必须按 ADR-039 的残余风险签核口径处理；不能仅以「实现优化」归类。

产品 Q2 选择保留后台全量 `quick_check`，因此未检查分片的暴露窗口应从「最长 7 天」修正为「启动写门打开后至后台全量检查完成前」；这显著降低残余风险，但 ADR 文本和测试必须明确该行为。产品 Q4 接受残余风险，仍需安全/QA 签核与故障注入证据。

## 4. 风险清单

### P0（阻塞签署/实施/验收）

1. **P0-1 验证不可证明**：ADR-040 §4 的测试/数值与当前代码、测试、M10-10 证据相反；选择性实现被回退，当前仅有 ADR-039 全量回退证据。若按现文签署，无法判定「选择性检查」是否被验证。
2. **P0-2 主库单独变脏漏检**：主库指纹变化、全部分片指纹未变时，按字面不检查主库；主库含 `messages`/`runs`/`audit_log`，存在漏检窗口。
3. **P0-3 `background_check_completed`/`clean_start_count` 语义未定义**：选择性检查后可能错误标记「后台检查完成」并让下一次启动严格跳过；或永远无法进入严格跳过，优化失效。产品 Q2 保留后台全量后，必须把该标志绑定到后台/周期全量检查，而不是选择性启动检查。
4. **P0-4 G13 范围冲突**：产品 Q1=B（G13 前实施）与 ADR「不进入 G13」文本直接冲突；没有新任务 ID、M10-10 补充证据和 G13 条件更新。

### P1（高风险，实施前闭环）

1. **P1-1 sidecar 前置匹配条件不完整**：`background_check_completed`、WAL=0、逐库 `schema_version`、分片集合/`shard_id`、主库指纹缺失等未列入。
2. **P1-2 周期检查口径冲突**：「每 20 次启动」vs「每 20 次干净启动或 7 天」；7 天未验证；`last_full_check_at=None` 行为未定义。
3. **P1-3 `health`/UI/验收指标语义未定义**：x/8、`state=ok`、`storageCheckCompletedAt` 在只检查部分分片时如何表达；产品 Q3=A 已确定方向，但字段/UI 未落实。
4. **P1-4 指纹字段定义不清**：`last_seq` 是否参与启动比对未定义；若参与，`MAX(seq)` 扫描会破坏 `initialize ≤1.5s`；`mtime` 兼容性未定义。
5. **P1-5 后台全量检查未写入 ADR**：产品 Q2=A 保留 ADR-039 的干净启动后台全量 `quick_check`，但 ADR §2 第 6 项仍写「未检查分片由周期完整检查兜底」，二者矛盾；需写明后台全量与周期检查的双层兜底关系。
6. **P1-6 流程/基线缺失**：未声明修订 ADR-039、未升版设计/P2/UI-UX、无新任务 ID/证据计划；「实现优化」不能覆盖 D-039-2/3/5 的行为变化。
7. **P1-7 无失效条件/回退触发器**：缺少「漏检故障注入失败/性能不达标/安全不接受」→ 回退 ADR-039 的判定。
8. **P1-8 优化收益未证明**：缺少 dirty 1/2/4/8 分布与冷缓存复测；「多数异常退出只影响 1–2 片」无证据；8 片全脏时无收益；保留后台全量后收益仅限缩短启动写门。
9. **P1-9 残余风险签核未完成**：产品 Q4=A 已接受，但 ADR 未写入暴露窗口/最大损坏范围，安全/QA 未签核，缺少「干净指纹+页级损坏」故障注入。

### P2（优化/表达）

1. **P2-1 `mtime` 假阳性/旧 sidecar 兼容**：杀毒/索引/时钟/复制会改 mtime；旧 sidecar 缺字段的比对行为未定义。
2. **P2-2 「多数异常退出只影响 1–2 个分片」缺少数据**：应引用或补充崩溃注入的脏分片统计。
3. **P2-3 「主库很小」缺少容量边界**：主库含 `messages`/`runs`/`audit_log`，大数据集下需测量。
4. **P2-4 术语/引用不精确**：「脏分片/指纹变化/原严格 sidecar 行为/周检/每 20 次启动」混用；缺 D-039-5、UI-UX S-00、P2 DoD、M10-10 证据引用。

### 5.3 需要架构决策的问题

1. **主库单独变脏**是否必须独立触发主库 `quick_check`？（建议：是；按 ADR-039「主库 + 分片」不遗漏。）
2. **`background_check_completed` 的语义**：是否拆成 `startup_check_completed` 与 `background_check_completed`？选择性检查通过后是否允许写 `true`？（按产品 Q2，建议不允许；仅后台/周期全量成功后置位。）
3. **`last_seq`/`schema_version`**：是否参与启动快速比对？若不参与，是否在 ADR 中明确为「记账字段」？`mtime` 是否只作辅助？
4. **`storageCheckCompletedAt`** 是否拆分为「启动检查计划完成」与「全量完整检查完成」？P2 性能矩阵/G13 证据用哪个？
5. **新任务/证据**：按产品 Q1=B，ADR-040 由哪个任务实施/复测？建议明确 `M10-14` 或 `M10-10 补充`，并列出 `verify:*` 与故障注入。
6. **回退开关**：是否需要配置/常量开关（如 `AETHER_STARTUP_CHECK_MODE=full|selective`）以便回退？若需要，按设置键/常量规则登记。
