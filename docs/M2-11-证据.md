### DoD3 去重（插件 delta 前缀消费 + final-only 后缀）

- 集成：默认路径 `deltas == message.completed`（token 级，`message.delta` >3 条）；`dedupe:suffix` 场景 final-only 后缀恰好补发 1 次。
- 单测（`dsh-delta.test.ts`）：精确覆盖无重复；后缀补发；committed 落后于流式（渐进 committed）不重发不兜底。

### DoD4 权限（100% 回环、零直通；复用 M2-10 探针）

- 集成 `tool_events_and_permission_loopback_are_full`：allow 路径把 `permission.request` 通知直接交给 M2-10 的 `PermissionLoop::dispatch`，探针 `zero_passthrough()` 且 `requests_received == 1`；deny 路径手工 `permission.resolve` 后工具收口 `tool.call_failed`；两次 ask 恰好 2 条通知（无直通、无重复）。
- 请求形状与 `PermissionLoopRequest::from_params` 对齐：`{request_id, session_id, run_id, resource, action, target, ...}`（`resource=fs.write/action=write` 集成断言）。
- 适配器 `permission.resolve` 返回 `{resolved, decision}`；未决议超时（压测 200ms）→ 默认 deny（D9 300s 口径的适配器侧兜底，TS 用例覆盖）。

### DoD5 兜底（丢弃 end / 截断通道 → 按 ACP final 重建）

### DoD6 通道清理（dispose 后残留通道数 = 0）

- 集成：`session.dispose` 响应 `residual_channels == 0`；dispose 后 `session.send` → `1005`；TS 探针 `residualChannels() == 0`。

### DoD7 20 次回归（终态零挂起；帧级丢失率 ≤1%；平均长度偏差 ≤5%）

- 集成输出：`完成 20/20；挂起 0；帧级丢失率 0.0000；平均长度偏差 0.0000`（夹具口径；真实 DSH 见 §5 opt-in）。

### DoD8 合规（不修改 DSH 源码 / 不拷贝 hermes 代码 / 事件契约记录）

## 4. 边界与偏离（相对 ADR-002 / M2-11 DoD 的实现口径）

1. **Codex `native_id` 别名**（ADR-008 §3.3）：`thread_id` 服务端生成、不可预生成；适配器返回 ULID 别名并持久化 `别名→thread_id`，对外保持 ADR-005 的 Mode R 语义。若后续引入回写通道可无痛切换。
2. **版本门闩信号通道**（ADR-008 §3.4）：DSH pin/契约帧失败经 `initialize` 应用码 `1003` 上报，监督器映射为 `disabled + version_mismatch`；不改变 hello 通道的既有协议 major 校验。
3. **ACP 权限选项映射**：allow 优先选择 `always/session` 选项，其次 `allow`，最后第一个；deny → `cancelled`；未决议超时默认 deny。
4. **`usage_update` 不伪造 usage**：ACP 只提供上下文占用（非输出 token），适配器仅记录诊断（spike 已知坑 15），`run.completed.usage` 缺省。
5. **DSH 会话不做 `session/close` on shutdown**：会话持久化是 Mode R 的依据；应用退出经 stdin EOF 收口（spike 已知坑 18），显式 `dispose` 才关闭会话。
6. **常量级参数**（AGENTS §3 MAY，记录于本证据）：Codex/DSH 适配器 run 硬超时 30min（核心 120s 断流看门狗优先）；权限等待 300s（D9 同口径）；插件契约帧等待 5s；DSH 默认 profile `acp`。

冷启动竞态（根因 + 官方解法，2026-09-22）：**settings 声明的 provider 路由注册是异步的**——
`dsh-llm-pi-ai` 在 apply 时以空 `providers` 调用 `ensureRegistrationFacts()`（`routes.length === 0`
直接返回、不注册），仅当异步注入的 settings 文档到达（`ctx.inject(["settings"])` → `setSource`/`onChange`）
才注册路由；`dsh-acp-app` 不等 settings 就绪即开始服务，窗口内 `session/new` 解析 provider 失败
（实测 1/5；上游 0.1.6-alpha.2 同路径未改）。对照官方 `deepseek-official` 在 apply 时**同步**注册。

**官方解法（已实现）**：`dsh-settings` 的 `installSection(..., base=插件行 config, user=settings)`
是「composition base + 用户覆盖」分层。把 provider 定义放进 overlay 的 `llm-pi-ai` 行
`config.providers`（适配器 `--dsh-provider-config <inline-json|file>`，核心从同一份物化结果传入），
路由即在插件 apply 时同步注册，竞态从构造上消除；settings 仍是用户覆盖层。
验证：同一实验台（全新 HOME + 立即 `session/new`）基线 1/5 失败 → composition base **6/6**
全部在 2.4–2.7s 即带 streamax 路由；全新 HOME 真实适配器 E2E **3/3 PASS**（基线 3.27s、
Mode R/中断正常、overlay 含 `llm-pi-ai` 行）。夹具层另加确定性回归：
`FAKE_DSH_NEW_FAILS=2` → 有界重试后成功、预算耗尽（=999）→ 失败不无限阻塞（TS 34/34 通过）。

### 5.2b DSH 真实权限 ask 回环（零直通）

环境：DeepSeek **官方 API**（provider `deepseek-official`，model `deepseek-v4-pro`，密钥经
`DEEPSEEK_API_KEY` 注入，不入库）；沙箱以 `DSH_PERMISSION_MODE=read-only` 启动（写入需沙箱升级
→ DSH 默认 `approval: ask` 触发 `session/request_permission`）；驱动对 `permission.request`
**延迟 1.2s 决议**，以证明适配器阻塞在回环上而非直通。

```

PASS  权限 ask 回环（deny，零直通）（ask=1；映射 tool.call_started 1/1；收口晚于决议 1；决议延迟 1200ms）
```

断言链（每条 `permission.request`）：

1. `request_id`/`session_id`/`run_id`/`tool_call_id` 齐备，形状与 M2-10 `PermissionLoopRequest`
   兼容（`resource`/`action`/`target`）；真实 ACP ask 只带 `toolCallId`，适配器用前置 `tool_call`
   跟踪补全：实测映射为 `tool_name=write / resource=fs.write / action=write`；
2. 与 `tool.call_started` **一一映射**（1/1，零直通：不存在未经回环即执行/收口的工具）；
3. 工具收口时间 **晚于** `permission.resolve`（延迟 1.2s 决议，allow 场景 1/1 收口在决议后）；
4. deny 场景：决议为 reject → 工具不成功收口，run 仍达终态；
5. 适配器仅转发 ask、绝不自行执行工具（进程内行为边界，设计 §2.1 第 4 条）。

证据：`scripts/test/.tmp/m2-11/real-dsh-2026-09-22T08-41-58-034Z/summary.json`（allow）、
`real-dsh-2026-09-22T08-38-28-653Z/summary.json`（deny）。
