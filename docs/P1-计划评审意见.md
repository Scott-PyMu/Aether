## 1. 总体结论

**文档完整性**：P1 计划的**主体映射完整**。设计 §5 P1 的 8 项新增能力、4 项决策变更、4 项退出标准，以及「完整审计查询/导出」这一 P1 关联交付，**逐条都有任务承接**（见 §2 核验矩阵 OK 行）；依赖全景、并行分组、量级计数（S 0 / M 7 / L 10 = 17 项）、门禁判定与回退动作内部自洽，量级分布经复核与逐任务标注一致。

**一致性状态**：计划与《设计文档》§5 + 附录 A + 《需求文档》§3.8 一致；但**与 ADR-010 §5 未决项、UI-UX 规格 §8 的 P1/P1+ 行不一致**——这两份基线中有 9 条 P1/P1+ 标签的条目未进入 P1 计划的任何位置（任务表、§8 条件表、§9 ADR 清单均无）。根因是计划 §范围（`:8`）自述的输入集只覆盖「设计 §5 P1 + 附录 A + 需求 §3.8 + 完整审计」，未纳入 ADR-010 §5 与 UI-UX §8。

**最大风险**：**UI-09 适配器消费映射 + 连通性测试**——基线三处（设计附录 A `:733`、需求 §3.8 `:155`、设计 D10 `:556`）均标 P1，计划 §8 却把它降为条件项，而该条件项的触发条件「UI 入口已占位（toast「P1 开放」）」**在 P0 已由 M3-11 满足**（`apps/desktop/src/ProvidersPage.tsx:385-392`；断言 `apps/desktop/src/m3_11_providers.test.tsx:281-296`）。按计划自身的触发规则它现在就该排期，实际却无任务 ID——即「P0 已交付一个承诺 P1 开放的入口，而 P1 计划没有承接它」，属对外可见的承诺悬空。其次是 4 项横切承接缺失（附录 C/CI 脚本契约、设置键白名单、UI 锚点与文案、`runtime.status_changed` 发射点），它们不影响计划完整性，但会让 P1 首次动工即撞门禁。

## 4. 风险清单

**P0（阻塞实现或验收）**：无。

**P1（高风险）**

1. **对外承诺悬空**（问题 1）：P0 已交付「连通性测试将在 P1 开放」入口，P1 计划无承接 → 进入 P1 后该按钮仍是 toast，用户可感知的承诺落空。
2. **CI 首次动工即红**（问题 9/10/11）：P1 一旦落 `0004+` 迁移与新设置键，附录 C 双向校验、索引计数常量、设置键白名单、UI 锚点四道门禁同时触发，而四者均无任务承接。
3. **链路断裂成片**（问题 4–7）：4 项基线标 P1/P1+ 的能力在计划中零出现，若不在 P1 计划冻结前裁定，将顺延到「无人负责」状态（P2 计划尚未生成，且 §11 只说 P2 起另行生成）。
4. **隐含前置未登记**（问题 12）：`runtime.status_changed` 被当作既有能力，M7-01 的关键 DoD 依赖一个当前不存在的事件通路。
5. **安全边界未定界**（问题 3）：三档模式中的「完全权限」若被实现为可放宽 `exec`/`net` 或工作区外写，将直接违反 D9 与信任级声明（AGENTS §2.7、设计 §2.1 第 4 条禁止把权限门表述为隔离）。

**P2（优化建议）**

6. 工作区树/多工作区（问题 6）与 Agent 预设（问题 7）虽标 P1/P1+，但两者地基已在 P0 落地，纳入 P1 的边际成本可控；如顺延，需改写标签以免长期悬空。
7. Linux 打包口径统一（问题 13）、一键归档按钮验收落点（问题 14）、运行期切换与模型删除的阶段归属（问题 8）。
