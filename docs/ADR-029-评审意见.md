## 1. 总体结论

**文档完整性**：结构完整（背景/决策/目标架构/协议/安全/数据/前端/打包/任务/门禁/风险/备选/后果/变更清单/开放问题/附录），12 条决策、14 个任务、9 个 Gate 均可定位；D1/D2/D7 与设计 v1.25 已同步，P2 计划 v0.2 已承接执行细节，AGENTS 的依赖方向/类型同步/目录边界已改。相对多数 ADR，本文件的可执行性基线属上乘。

**一致性状态**：命令面事实核对**通过**（63 个 `#[tauri::command]` 与附录 16.1 名称集合逐项一致；前端 70 处 `invoke`、1 处 `onDragDropEvent`、46 个前端测试文件均与 ADR §1.1 数字一致）；但存在 4 类一致性缺陷：

1. **契约口径冲突**：单帧 2MiB 硬上限 + 超限重启 daemon 与 ADR-009「分页 ≤500、单条 ≤1MiB、不设聚合上限」冲突（P0-1）；`params` 是否保留 Tauri 的 `{payload}` 包装未定义（P1-5）；错误码「32」把枚举值与稳定业务码混为一谈（P1-3）。
2. **时序预算冲突**：关闭序列内部预算 ≥8s 与 `shutdown` 5s、T11「10s 内退出」三者不可同时成立（P0-2）；启动顺序把窗口创建放在 daemon 完成适配器预热之后，与 M9-09「窗口可见 ≤1.5s」冲突（P1-2）。
3. **安全/回退闭环缺口**：跨壳数据目录锁只有 daemon 侧取锁，回退 Tauri 壳不取锁（P1-1）；路径复核清单漏 `backup_create`/`export_diagnostics`（P1-8）；preload 白名单与 §7 的 `webUtils` 依赖自相矛盾（P1-7）。
4. **验收可证明性缺口**：新增壳级致命页/Keychain 重授权提示但声明 UI-UX 不变（P1-11）；G7「P0 T1–T15 复跑」含 T14（bindings 生成）与 P0 Tauri 安全基线等不可执行项（P1-12）；协议枚举/能力词表缺失导致 G1 golden fixtures 无法固化（P1-6）。

**最大风险（按影响排序）**：

- **R1（P0-1）**：大历史会话补读/审计查询必然产生 >2MiB 响应 → 连接被关闭 → main 重启 daemon → 在途 run 被杀、UI 反复重启；G3「控制事件不丢 + 补读」与 G7 复跑无法通过。
- **R2（P0-2）**：正常退出时 main 可能在 daemon drain/checkpoint 完成前强杀进程树，导致「已确认消息零丢失」（T4）在**正常退出路径**上失守；若延长等待则 T11「10s 内退出」失守。
- **R3（P1-1）**：迁移窗口内旧 Tauri 包与 Electron 包可同时打开同一数据目录（旧壳不取锁），触犯设计 §2.4 自列的「双开导致库损坏是最高代价的故障」底线。
- **R4（P1-9）**：M9-08 移除 `@tauri-apps/api` 后，「G7 前 Tauri 构建保持可用 / 任一门禁失败回到 Tauri」在 HEAD 上不再可构建，回退对象未定义。

## 2. 问题列表

### 2.1 P0（阻塞实现或验收）

#### P0-1 单帧 2MiB 硬上限 + 超限重启 daemon，与 `messages_page` 无聚合上限的既有契约冲突

- **问题**：ADR §4.1 规定 UI↔daemon 单帧上限 2MiB，「超限：返回 `too_large`（若还能写响应），随后关闭连接，由 main 重启 daemon」；§4.7 又规定控制队列满时「主动断开连接，main 重启 daemon」。但设计 D7 `messages_page` 行的载荷边界是「单条 ≤1MiB、分页 ≤500（events/messages 各自），**不设聚合上限**」，`audit_query` 也是 ≤500 行。500 × 1MiB 的合法响应可达数百 MiB，必然超过 2MiB；一次 UI 侧超限请求（renderer 传超限参数）也会触发 daemon 重启，杀掉全部在途 run。
- **依据**：ADR-029 §4.1、§4.7；《设计文档》D7「`messages_page`（ADR-009；响应契约登记）」载荷边界句；ADR-009 附录 A（响应契约表）；《设计文档》D8「超限时该适配器订阅者整体切换 journal 补读模式，不反压 reader、不影响其他适配器」。
- **风险**：G2/G3/G7 无法通过；长会话/大审计库成为**必然触发**路径；「补读恢复」被 daemon 重启打断，UI 出现重启风暴；`too_large` 既是既有 `aether_code`（32 枚举之一）又被当作传输级处置，语义混用。
- **建议**：① 明确区分「请求帧上限」与「响应聚合上限」，并为 `messages_page`/`audit_query` 等大响应命令定义**响应体积预算或分批游标**（多帧分批、客户端合并），口径回写设计 D7 与 ADR-009；② 明确「超限只对本请求返回 `too_large`，**不重启 daemon**」，仅在无法解析/无法保序的帧错误时断连；③ 把两种处置分别写成 G2/G3 的 golden fixture 与故障注入用例。

#### P0-2 关闭序列时序预算冲突，正常退出路径可能强杀 daemon

- **问题**：ADR §3.6 第 1 步「发送 `shutdown` RPC（5s）」，第 2 步要求 daemon 完成「适配器 `shutdown` RPC 5s → 进程组/Job Object 回收 → 写队列 drain 3s → 关卡读连接 → `wal_checkpoint(TRUNCATE)` → 关写连接」，第 3 步「main 等待 daemon 退出；超时则 taskkill /T /F」但**未给超时值**。内部预算已 ≥8s（不含 checkpoint 与回收耗时），与 5s RPC 等待、附录 D T11「10s 内退出」三者不可同时成立。
- **依据**：ADR-029 §3.6；《设计文档》D2「关闭序列（ADR-004/ADR-029 §3.6）」（同序）；《设计文档》附录 D T11「适配器无响应下退出应用｜10s 内退出；无孤儿进程」。
- **风险**：按现有文字实现，正常退出会在 daemon drain/checkpoint 前发 `taskkill /T /F`，未落盘事件丢失，`T4`「已确认消息零丢失」与 G5 失败；若为保数据延长等待，则 T11 失败。**这是门禁级冲突，不是实现细节**。
- **建议**：定义**单一退出预算**与阶段语义：`shutdown` 请求立即回执（不等于关闭完成）+ 以「进程退出/锁释放」为完成信号；daemon 内部预算写死 ≤7s 且保证「drain 先于 checkpoint 完成」；main 总等待 ≤9s、末段强杀；把「预算表 + 强杀点」写入 §3.6 与 T11/G5 的验收条件。

### 2.2 P1（高风险：边界未定义/异常流程缺失/安全风险/验收不可证明）

#### P1-1 跨壳数据目录锁未闭环；计划允许的「退化」与设计底线冲突

- **问题**：ADR §2 D-029-9 与 §6 断言「旧 Tauri 构建与 Electron 构建**不得**同时打开同一数据目录（跨壳数据目录锁）」，但锁由 **daemon** 在启动时获取（§3.5-3）；回退用的 Tauri 壳不实现该锁，因此该断言只覆盖「Electron 已运行」一侧。P2 计划 M9-09 DoD5 又允许「否则退化为 SQLite `busy_timeout` + 明确提示」，与设计 §2.4 把「双开」列为最高代价故障的底线口径冲突。
- **依据**：ADR-029 §2 D-029-9、§6「跨壳互斥」、§3.5-3、§9.3；`docs/P2-架构迁移-实施计划与验收标准.md` M9-09 DoD5；《设计文档》§2.4「单实例锁 + 数据目录检测（A4）｜双开导致库损坏是最高代价的故障」。
- **风险**：迁移窗口内（G6 安装升级验证前）旧 Tauri 包仍可能被启动 → 两进程并发写库/并发迁移 → 库损坏（不可逆）。ADR 的「不得同时打开」是不可验证的断言。
- **建议**：二选一并写进 ADR：① Tauri 回退构建在 M9-09 同步获取同一锁（并说明这是回退基线唯一允许的改动）；② 明确「回退 = 冻结的上一版 Tauri 安装包 + 强制先退出 Electron」的运维口径，并在 G5/G8 增加「陈旧 Tauri 包检测/提示」验收项。禁止以 `busy_timeout` 作为互斥替代。

#### P1-2 启动顺序把窗口创建放在 daemon 完成预热之后，与「窗口可见 ≤1.5s」冲突

- **问题**：§3.5 顺序为：spawn daemon → 取锁 → `initialize`（5s）→ daemon 执行「DB 打开 + `quick_check` → 孤儿清理 → 迁移 → 适配器预热」→ **第 6 步 main 创建 `BrowserWindow`**。而 M9-09 DoD1 的启动阈值是「窗口可见 ≤1.5s；daemon ready ≤2s」。三运行时预热（各自 spawn + initialize，单适配器握手预算 10s）显然无法在 1.5s 内完成。
- **依据**：ADR-029 §3.5 第 4–6 步；`docs/P2-架构迁移-实施计划与验收标准.md` M9-09 DoD1；《设计文档》D5「预热：应用启动即启动全部 enabled 适配器并完成 `initialize`」；《设计文档》D6 `initialize` 超时 10s。
- **风险**：实现者只能二选一（违背门禁或违背顺序）；「启动 1.5s/2s」作为 G7 门禁无稳定判定口径（是否含预热、是否含迁移），签核时必然扯皮。
- **建议**：改为「先创建窗口/显示启动页（可达 S-00），再等待 daemon ready；`initialize` 只要求 daemon 进程可用 + 数据目录/阶段可读，不等待适配器预热」；并把 1.5s/2s 的口径（是否含迁移/预热/冷启动次数）写入 ADR 与 M9-09 DoD。

#### P1-3 错误码「32」口径混用；`as_str()` 不是完整 aether_code 映射源

- **问题**：§4.3 称「`data.aether_code` 保留 **32 个既有稳定业务码**（`invalid_value`、`session_busy`、`startup_blocked`、`pause_unsupported` 等）」；§16.2 称「`IpcErrorCode::as_str()` 是唯一映射源；`aether-app` 导出 `error_codes.json`，TS 客户端生成 union；CI 校验 32 个值不漂移」。但仓库事实是：`IpcErrorCode` 的 32 个枚举值**不包含** `session_busy`/`session_paused`/`storage_backpressure`/`memory_conflict`/`permission_not_pending`，这些是独立「稳定业务码」，ADR-018 明确「稳定业务码不入附录 B、不计入」。因此「32 个稳定业务码」与「`as_str()` 是唯一映射源」均不成立，G2「32 错误码逐项可达」无法判定验收集合。
- **依据**：ADR-029 §4.3、§16.2；ADR-018 附录 A-7/§附录 B 计数说明「稳定业务码（`session_busy`/`session_paused` 等）不入本表、不计入」；`crates/aether-tauri/src/ipc/error.rs`（32 变体，无 `SessionBusy`）；`crates/aether-control/src/lifecycle.rs`（`SessionBusy => "session_busy"`）；`crates/aether-tauri/src/session_backend.rs` 注释「`session_busy` / `storage_backpressure` / `persist_degraded` 的专用 IPC 错误码」。
- **风险**：生成的 TS union 会漏掉 UI 实际分支的码（UI-UX 文案表引用了 `storage_backpressure`、`memory_conflict`）；M9-04 的「32 错误码逐项可达」可被两种口径各解释一次；契约漂移在主 UI 侧不可见（daemon 只做透传）。
- **建议**：分离两套台账并在 ADR 登记：①「`IpcErrorCode` 枚举 32」；②「稳定业务码（不计数，清单 + 归属模块）」。`error_codes.json` 覆盖两侧全集并加 `kind` 标注，CI 校验两份计数；G2 明确「32 枚举 + N 稳定业务码」的验收集合。

#### P1-4 新增/未登记错误码与「`initialize` 之前失败」的上报通道未定义

- **问题**：① §3.5-3 锁失败「返回 `already_running` 并退出」——`already_running` 在仓库中是 `RuntimeControlReport.outcome` 的取值（ADR-015），不是错误码；若作为 `aether_code` 使用，属 ADR-006 附录 B「新增取值须走 ADR」的未登记新增（且与 outcome 同名不同义）。② §4.2 `protocol_mismatch`、§4.5 `cancelled`/`timeout` 同属未登记命名。③ 更关键：锁失败发生在 `initialize` **之前**，此时没有可响应的请求 id，ADR 未定义 daemon 如何把「数据目录被占用」这一具体原因上报给 main（首帧 error？stderr + 退出码？）。
- **依据**：ADR-029 §3.5-3、§4.2、§4.5、§4.3；ADR-006 附录 B 说明「新增取值须走 ADR」；ADR-015 附录 C-1（`outcome` 取值域含 `already_running`）；`crates/aether-tauri/src/runtime_control.rs`（`AlreadyRunning => "already_running"`）。
- **风险**：G2 错误码计数口径再次失真；main 只能靠「进程退出 + 模糊提示」区分锁冲突与崩溃，UI-UX 的「另一个 Aether 实例正在使用数据目录」无法稳定呈现；后续 M10 多客户端会重复踩同一坑。
- **建议**：明确三类命名空间（JSON-RPC 传输码 / `aether_code` / 内部 outcome），未登记码先按 ADR-006 附录 B 增行；定义「预 `initialize` 阶段」的唯一结构化失败帧（如首帧 `{"jsonrpc":"2.0","id":null,"error":{...}}` + 退出码表），并在 G1 增加 fixture。

#### P1-5 `params` 是否保留 Tauri `{payload}` 包装未定义

- **问题**：§4.3 说「`params` = 现有请求 DTO 的 JSON 形状（与 Tauri invoke 的 payload 一致）」，「成功：`result` = 现有响应 JSON（`JsonPayload` 解包后的值）」。现状是：前端 70 处 `invoke` **全部**以 `{ payload: ... }` 传参（如 `invoke("session_list", { payload: filter })`），Rust 命令签名统一为 `fn session_list(payload: ...)`，响应侧才有 `JsonPayload` 解包。即「请求保留包装、响应去包装」的不对称现状。ADR 未裁定 daemon 的 `params` 是内层 DTO 还是 `{payload:{...}}`，也未规定无参方法的编码（`health`/`backup_list` 现状为省略 payload，`rules_list` 传 `{payload:null}`）。
- **依据**：ADR-029 §4.3；`apps/desktop/src/session.ts`/`settings.ts`/`providers.ts` 等 70 处调用形态；`crates/aether-tauri/src/ipc/commands.rs` 命令签名；《设计文档》D7「无参数（严格解析：`null`/缺省/空对象合法）」。
- **风险**：这是 63 条命令的**全局契约**；实现时二选一，选错即整条链路返工，且 G2「Tauri/daemon 对照 0 差异」会因包装层差异直接失败。
- **建议**：在 §4.3 明确裁定（推荐：`params` = 内层 DTO、去掉 `payload` 包装；无参方法 `params` 省略或 `null` 等价，`{}` 亦合法），并给出 2–3 条 golden fixture（有参/无参/空对象）作为 M9-03 冻结物。

#### P1-6 协议契约元素不完整：枚举/能力词表/通知登记名缺失，事件通道名三处不一致

- **问题**：① `initialize` 与 `daemon.status` 的 `phase` 取值未枚举；② `capabilities` 请求含 `browser-view`、响应不含，但**协商语义**（并集/交集/未知项忽略/是否门禁）未定义；③ `daemon.status`、`permission.pending` 两个通知在 ADR §4.4 定义，但**设计 D7 没有 `daemon.status`**（v1.25 D7 只提 `aether.event`/`permission.pending`/`dialog.pick`）；④ 事件通道名三处不同：设计 D7「单通道 `aether://event`」、ADR §4.4「`aether.event`」、ADR §5.1「`webContents.send('aether:event')`」（层次不同但命名未统一说明）。
- **依据**：ADR-029 §4.2、§4.4、§5.1；《设计文档》D7 实现要点「事件通道：单通道 `aether://event`」与 ADR-029 传输增量段；M9-03 DoD2「版本/能力/数据目录/启动阶段返回」。
- **风险**：G1 要求 golden fixtures 与 `initialize` 契约断言，枚举缺失导致 fixture 无法固化（只能写成「任意字符串」）；未知 capability 的处理规则缺失会在 Electron 版本错配时报错或静默降级；`daemon.status` 未入设计意味着「启动页/横幅」的协议来源没有设计依据。
- **建议**：在 D7 增「UI 通道方法/通知登记表」（命令 63、通知登记表、服务端请求表），给出 `phase`/`capabilities` 枚举与未知值策略（忽略 + 诊断）；统一通道名为 `aether:event`（IPC channel）与 `aether.event`（协议 method）并说明映射；把 `daemon.status` 同步进 D7。

#### P1-7 preload 白名单与 §7 拖拽方案自相矛盾

- **问题**：§5.1 规定 preload 只暴露 `rpc()`/`onEvent()`/`offEvent()`/`getVersion()`，并「**不暴露** `ipcRenderer`、`require`、`process`、`fs`、`child_process`、**任意 channel**」；但 §7 要求「拖拽：`SessionWorkbench.tsx` 的 `getCurrentWebview().onDragDropEvent` → DOM `drop` + **preload `webUtils.getPathForFile`**」。`webUtils` 未列入白名单，且 `sandbox:true` 下 renderer 无法直接 `require('electron')`。
- **依据**：ADR-029 §5.1、§7；`apps/desktop/src/SessionWorkbench.tsx:1217-1218`（唯一 drag-drop 处）；M9-10 DoD2（preload 白名单断言只列 4 项）。
- **风险**：实现时要么偷偷加宽白名单（与 verify:security 断言冲突），要么拖拽功能不可用（G4「拖拽」验收失败）。
- **建议**：白名单显式增 `pathForFile(file) → string`（最小面、只返回路径字符串），并在 §5.1/M9-10 断言中同步；说明 sandbox 下 `webUtils` 只能经 preload 转发的原因。

#### P1-8 路径复核清单不完整（漏 `backup_create` / `export_diagnostics`）

- **问题**：§5.3 列出「`artifact_add`、`workspace_set`、`startup_migrate`、`backup_restore`、`session_export`、`archive_export` 的路径校验不变」，但仓库现状还有两个**接收用户选择目录**的命令：`backup_create`（`target_dir`）与 `export_diagnostics`（目标目录），二者前端均复用 `startup_pick_target` 选路径。ADR 又规定 main/renderer 不可信、daemon 为最终权威，因此这两个命令必须在 daemon 侧做 canonicalize/可写/空间护栏（D13 `db+wal ×1.2`）。
- **依据**：ADR-029 §5.3、§4.6；`apps/desktop/src/backup.ts:124-131`（`backup_create` 携 `target_dir`）；`apps/desktop/src/diagnostics.ts:39-46`（`export_diagnostics` 携目标目录）；《设计文档》D13「备份/导出目标支持外部路径……校验目标可写且可用空间 ≥ 当前 `db+wal` ×1.2」。
- **风险**：口径漏项 → 实现按 ADR 文本只复核 6 条命令，两个「写文件到用户指定目录」的命令成为校验盲区（路径逃逸/磁盘写满/覆盖既有文件）。
- **建议**：把清单改为「所有含路径参数的命令」的**生成式清单**（从 DTO 生成，CI 断言集合），或至少补齐这两条；verify:security 增「路径参数命令全集」断言。

#### P1-9 回退基线的可构建性/回退对象未定义，与 M9-08「移除 @tauri-apps」冲突

- **问题**：§3.3/§9.3 反复声明「迁移期 Tauri 构建保持可用」「任一门禁失败：回到 Tauri」；但 §7 与 M9-08 DoD3 要求把 70 处 `invoke` 全部改为 `client.*` 并从依赖移除 `@tauri-apps/api`，G4 通过条件为「无 `@tauri-apps` 运行时」。共享同一个 renderer 的前提下，M9-08 之后 HEAD 的 Tauri 构建**不可能**再产出可用 UI。ADR 未说明「回到 Tauri」到底是：回滚代码 / 安装上一版冻结包 / 保留双传输适配层。
- **依据**：ADR-029 §3.3、§7、§9.3、§10 G4；`docs/P2-架构迁移-实施计划与验收标准.md` M9-08 DoD3、M9-14 DoD2、§6 回退步骤；`docs/P2-架构迁移-实施计划与验收标准.md` M9-09 DoD5（Tauri 回退构建仍存活）。
- **风险**：G4 与「Tauri 可用」互为前提冲突；G5/G6 失败时的回退路径不可执行（回退对象不存在）；G7「旧 Tauri 基线对照」与 M9-14 回退演练的证据链断裂。
- **建议**：在 ADR 明确「回退 = 冻结的上一版 Tauri 安装包（记录版本 + 哈希 + 发布日期）」并给出「HEAD 不再构建 Tauri」的时点（建议 M9-08 起）；若确需 HEAD 双传输，则在 §7 增加 transport 适配层与退役时点，并同步 G4 措辞（改为「生产 renderer 无 `@tauri-apps`」）。

#### P1-10 控制事件队列满即重启 daemon，与 D8 既有 journal 补读机制冲突

- **问题**：§4.7 规定「控制队列满 → 主动断开连接，main 重启 daemon」。设计 D8 对同类场景的既定机制是「该适配器订阅者整体切换 journal 补读模式（清空内存积压、从磁盘重读），**不反压 reader、不影响其他适配器**」。用重启 daemon 替代补读，等于用「杀在途 run」换取队列回落。
- **依据**：ADR-029 §4.7；《设计文档》D8「控制事件投递」「失败场景与应对（并发专项）」控制投递积压行；ADR-029 §4.4「UI 仍以 `last_seq` 补读」。
- **风险**：一次 UI 慢消费（renderer 卡顿/后台窗口）即可触发全量重启，破坏「主 UI 崩不影响数据/运行」的既定体验；重启期间在途 run 全部收口为失败，用户可感知。
- **建议**：沿用 D8：先切 journal 补读 + 丢 delta + 诊断计数；仅当「无法保序/无法补读」时才断连，且断连粒度尽量限于该连接的重建（不重启 daemon 进程），或明确「重启」只在连续 N 次补读失败后触发并记录审计。

#### P1-11 新增壳级 UI 表面未登记，却声明「UI-UX 锚点/文案不变」

- **问题**：§3.5-8 要求「daemon 无法启动/握手失败：main 显示**壳级致命页**（含日志路径、重试、退出），不加载主 UI」；§3.7 要求 `core_not_ready` 横幅；§5.4 要求 Keychain preflight 失败时「UI 提示需要重新授权/重新输入密钥」。但 §7 声明「UI-UX v0.14 的锚点/文案/布局不变；本 ADR 不改 UI 规格」，§14 声明 UI-UX「**不改**」。UI-UX v0.14 的界面清单为 S-00～S-11，**没有**「主 UI 不加载的壳级致命页」，S-01a 是启动门阻断页、S-09 是应用内「核心未响应」覆盖层。
- **依据**：ADR-029 §3.5-8、§3.7、§5.4、§7、§14；`docs/UI-UX-设计规格.md` §1.2 界面清单（S-00/S-01/S-01a/S-09）与「UI-UX 锚点 20」基线；ADR-029 §2「不改变」行与 §11。
- **风险**：新页面无锚点/无文案表/无验收口径 → G4「壳级错误页」无法做断言（M9-07 DoD4 只写「daemon 失败显示壳级错误页」，无文案/锚点）；测试与设计规格脱节；后续 UI 回归（M9-13 锚点无回归）无法覆盖。
- **建议**：把「壳级致命页」「Keychain 重新授权提示」登记为 UI-UX 新锚点（建议 S-12 / 或扩展 S-01a），给出文案、退出/重试行为、可断言属性（`data-*`），版本升 v0.15 并与 M9-07/M9-09 前置绑定；同时修正 ADR §7/§14 的「不改 UI 规格」表述。

#### P1-12 G7「P0 T1–T15 + P1 门禁复跑」含新架构下不可执行项

- **问题**：G7 通过条件含「P0 T1–T15 + P1 门禁复跑」。其中 T14 是「CI 重新生成 **bindings**（tauri-specta）→ `git diff --exit-code`」，而 bindings 在 M9-08 被 `types.ts`/`client.ts`/`command-manifest.json` 取代；P0 的 Tauri 安全基线（实施计划 M1-08 DoD2「`withGlobalTauri:false` 断言」）与 ADR-001 的「Tauri 产出 MSI/DMG」在新架构下同样不可执行。ADR 未给「复跑/替代/退役」分类。
- **依据**：ADR-029 §10 G7；《设计文档》附录 D T14；《实施计划与验收标准》v1.24 M1-08 DoD2、M4-05 DoD1；ADR-001；`docs/P2-架构迁移-实施计划与验收标准.md` M9-13 DoD2。
- **风险**：G7/G0 签核时无法给出「全绿」证据；若测试人员按字面执行 T14，会去找已退役的生成器；「不得静默跳过」与「无替代口径」冲突。
- **建议**：在 ADR §10 或 P2 计划 §2.15 增「P0/P1 门禁在新架构下的映射表」：复跑（T1–T13、T15）、替代（T14 → `protocol generate/check` + 63/59/4 计数；Tauri 安全基线 → M9-10 `verify:security`）、退役（ADR-001 Tauri bundler 口径 → D-029-10 electron-builder），并注明退役项的承接任务与证据。

### 2.3 P2（优化建议：表达/可维护性/一致性）

#### P2-1 12 条决策缺逐条「失效条件」，风险表缺 owner/触发条件

- **问题**：评审规则要求每个关键决策含「决策/实现方式/风险/缓解措施/失效条件」；ADR §2 的 D-029-1～D-029-12 无逐条失效条件与量化触发（设计 D1/D2/D7 有，但 ADR 层只给全局回退）。§11 风险表无 owner，与 P2 计划 M9-01 DoD4「每项有 owner/缓解/回退触发」不一致。
- **依据**：`评审要求.md` §三「技术决策检查」；ADR-029 §2、§11；`docs/P2-架构迁移-实施计划与验收标准.md` M9-01 DoD4。
- **风险**：决策失效时无法判定「触发即回退」，只能事后争论。
- **建议**：为 D-029-1（安全门禁失败阈值）、D-029-7（WebContentsView 不可行时的回退）、D-029-9（锁不可用）、D-029-10（MSI 升级不可行）补失效条件；风险表补 owner 列。

#### P2-2 数字基线漂移（`bindings.ts` 923 行 → 实测 1003 行）

- **问题**：§1.1 称 `bindings.ts`「923 行」，仓库实测 1003 行；其余数字（63 命令、70 处 invoke、1 处 drag-drop、46 个前端测试文件）核对一致。
- **依据**：ADR-029 §1.1；`packages/protocol/src/bindings.ts`（共 1003 行）。
- **风险**：基线数字被当成事实引用（M9-01 路由清单比对依赖这些统计），偏差会削弱证据可信度。
- **建议**：M9-01 用脚本生成统计（命令数/调用点数/测试数/bindings 行数）并归档，ADR 引用脚本输出而非硬编码。

#### P2-3 命令分组计数口径不一（§4.6 vs 附录 16.1）

- **问题**：§4.6 表把 `ref_pick` 计入「Electron 壳本地 4 条」、daemon 侧 artifacts 记 3、startup 记 2；附录 16.1 却把 `ref_pick` 计入 artifacts 组（4）、`startup_pick_target` 计入 startup 组（3）。总数 63 一致，但**分组计数**不同，直接对应 `command-manifest.json` 的 group 字段与 CI 校验。
- **依据**：ADR-029 §4.6、§16.1；§4.6「路由表由 `aether-app` 的 `COMMANDS` 清单生成……CI 校验 63/59/4 计数与名称集合」。
- **风险**：生成器与校验脚本按不同分组口径实现，CI 计数断言反复失败或写成两套。
- **建议**：以 §4.6 为唯一口径（壳本地 4 条不入业务分组），附录 16.1 的组头改为「按业务域统计（含壳本地命令）」并注明与 §4.6 的差异。

#### P2-4 `dialog.pick` 路由二义，且 M9 无消费方

- **问题**：§3.4 裁定「4 条壳本地命令由 Electron main 直接处理，不进入 daemon」，M9 不强制走 `AppHost`；§4.5 又说 `dialog.pick`「用于 `ref_pick`/`startup_pick_target` 的 daemon 侧实现（**若选择 daemon 路由**）」；M9-06 DoD4 要求交付 `dialog.pick` fixture「为 M10/P3 MCP elicitation 预留」。若改走 daemon 路由，59/4 → 60/3，破坏冻结计数与 G2/G0 基准。
- **依据**：ADR-029 §3.4、§4.5、§4.6；`docs/P2-架构迁移-实施计划与验收标准.md` M9-06 DoD4、M9-04 DoD4。
- **风险**：范围二义（做/不做都合理）→ 实现者可能实现两条路径；计数冻结物被破坏。
- **建议**：明确「`dialog.pick` 仅协议预留，M9 不由 `ref_pick`/`startup_pick_target` 使用（两者固定壳本地）；fixture 只验证协议形状，不接产品路径」；或若确定走 daemon，则同步改 63/60/3 与 G0 基线（需重新走 G0）。

#### P2-5 P2 阶段引入 P3/P4 承载，需求侧无对应登记

- **问题**：§1.2 把「UI-06 内嵌浏览器（P4）」「MCP/Node（P3）」列为 Electron 的直接触发；§2 D-029-7/D-029-8、§5.2 与 G5 的「WebContentsView 隔离」验收都要求在 M9（P2）落地。需求文档 §8 P2 交付物为「子 Agent、编排引擎、aetherd/HTTP API」，未含 Electron 壳、UI-06 PoC、MCP 承载；ADR §14 声明需求文档「不改」。
- **依据**：ADR-029 §1.2、§2 D-029-7/D-029-8、§5.2、§10 G5、§14；《需求文档》v0.18 §5「UI：Tauri / Electron + React」（允许但非要求）、§8 P2 行、UI-06 阶段列（P4）；《设计文档》§4#10「内嵌浏览器（UI-06）……P4」。
- **风险**：【阶段边界风险】P4 能力在 P2 产生实现与门禁义务，而需求侧无登记、无「砍一项换一项」对价记录；G5 的浏览器隔离验收在需求追溯矩阵中无来源。
- **建议**：在 ADR 显式登记「M9 的 `WebContentsView` PoC 属 P2 迁移使能，不构成 UI-06 阶段前移；完整交互仍 P4」，并在需求/UI-UX 侧补一行追溯（或由 M9-01 证据归档该裁定），避免后续把 PoC 当作 UI-06 交付。

#### P2-6 打包细节未决（universal 与 sidecar 架构、嵌套签名、entitlements/Keychain ACL）

- **问题**：§8.1 要求「macOS：DMG universal」「`extraResources`: `bin/aetherd`（按平台/arch）、`runtime-bundle/`（3 个适配器 + …）」；universal DMG 需要 universal（lipo）或分架构的 sidecar 与 runtime-bundle，ADR 未裁定。嵌套二进制（`aetherd`、适配器可执行文件）在 hardened runtime/公证流程中的签名顺序与 entitlements 未说明，而 §5.4 又要求 `aetherd` 可读旧 Keychain 条目。
- **依据**：ADR-029 §8.1、§5.4、§6；`docs/P2-架构迁移-实施计划与验收标准.md` M9-11 DoD1/DoD2。
- **风险**：G6 阶段才发现 universal 组合不可行或嵌套签名/公证失败；Keychain ACL 与签名身份的关系在 G5 才暴露（M9-09 真机演练）。
- **建议**：M9-01 冻结「universal 打包策略（lipo sidecar vs 双架构分发）」「嵌套签名顺序与 entitlements 清单」，M9-11 DoD 增「嵌套二进制签名/公证断言 + Keychain preflight 绑定签名身份」。

#### P2-7 覆盖率门禁迁移期排除 `aether-tauri` 与 T15 的关系未登记

- **问题**：§8.2 用 `cargo llvm-cov --workspace --exclude aether-tauri --fail-under-lines 70`（G8 后全量）；设计附录 D T15 为「Rust/TS 行覆盖 >70%」。迁移期把承载 2.29 万行、且正被抽取的 `aether-tauri` 排除，覆盖率口径与 T15 不一致，且排除期可能掩盖测试迁移遗漏。
- **依据**：ADR-029 §8.2、§10 G7；《设计文档》附录 D T15；`docs/P2-架构迁移-实施计划与验收标准.md` M9-12 DoD4。
- **风险**：G7 判绿但实际覆盖下降；「Tauri 边界测试等价迁移，不得删除后声称通过」的纪律缺少量化兜底。
- **建议**：登记「排除期 = M9-02 起至 G8」「排除期间以 aether-app/rpc/daemon 增量覆盖 + Tauri 删除文件清单核对替代」，并在 G8 恢复全量时给出对比表。

#### P2-8 锁的陈旧/迁移后归属与 `.aetherd.lock` 交互未定义

- **问题**：§3.5-3「daemon 解析数据目录（A4）并获取锁」与第 5 步「daemon 执行 D2 启动序列：数据目录检测（A4）→ DB 打开……迁移」顺序重叠；若 A4 阻断后用户 `startup_migrate` 成功，指针指向新目录，旧锁如何释放、新目录锁如何获取、新目录已被另一实例锁定如何处理，均未定义。锁的实现机制（句柄独占 vs 存在性标记）与崩溃后陈旧锁清理也未说明。
- **依据**：ADR-029 §3.5-3/5、§6、§9.3；ADR-006 附录 A.2（迁移链）；《设计文档》A4。
- **风险**：迁移成功后仍持旧目录锁/新目录无锁；存在性标记型锁在崩溃后导致「永远 already_running」，与「不得裸杀/台账」纪律冲突。
- **建议**：在 §3.5 增「锁生命周期」表：解析→取锁→迁移前释放→新目录重取→崩溃后陈旧锁判定（句柄存活 + PID/启动时间台账），并明确 `.aetherd.lock` 不参与数据迁移复制。

#### P2-9 `export_diagnostics` 读取 main 的 `shell.log`：跨进程写、脱敏、轮转与不可用场景

- **问题**：§4.6 规定 `export_diagnostics` 由 daemon 收集核心日志并「读取 main 写入 `<data_dir>/logs/shell.log`」。而 §3.5-2 要求 main 在数据目录解析前先把 stderr 写到平台临时日志，之后转写；daemon 启动失败（G4 硬失败场景）时主 UI 不加载，`export_diagnostics` 作为业务命令在启动门阻断/核心未起时不可用，恰好在最需要诊断时缺位。shell.log 的脱敏责任（密钥扫描）与轮转也未定义。
- **依据**：ADR-029 §4.6、§3.5-2、§3.7；《设计文档》D10（日志脱敏）、D11（诊断包来源）；UI-UX S-07（诊断导出入口）。
- **风险**：诊断包可能缺 shell 侧日志或含未脱敏内容；崩溃期无法取证，G4/G5 的失败分析成本上升。
- **建议**：明确 shell.log 的写入方/轮转/脱敏（由 main 脱敏后落盘）、daemon 只读快照；壳级致命页提供「离线导出诊断」入口（不依赖 daemon），并写入 M9-07/M9-10 DoD。

#### P2-10 debug 探针命令在 Electron 下的处置未定义

- **问题**：§1.1 提到现状「E2E 使用真实 WebView2 + debug probe」；仓库 debug 构建额外注册 5 个探针命令（如 `e2e_probe_report`，`ipc/commands.rs` 的 `#[cfg(debug_assertions)] handler` 注释明确 release 不包含）。ADR/计划未说明这些探针迁移到 daemon、改写为 Playwright，还是退役；`command-manifest.json` 的 63 计数不得包含 debug 方法也未写明。
- **依据**：ADR-029 §1.1、§8.2（`pnpm e2e:m9`）；`crates/aether-tauri/src/ipc/commands.rs:1065-1070`（debug 额外注册、release 不包含）；`crates/aether-tauri/src/probe.rs`。
- **风险**：E2E 证据链断裂（启动/健康/权限的可观测点消失），或 debug 方法混入正式契约。
- **建议**：在 §7/§8 增「debug 探针处置」：替换为 Playwright + daemon 侧 test-only 方法（`#[cfg(feature="test-hooks")]`），并在 manifest 校验里显式排除。

## 4. 风险清单

**P0**

1. **大响应击穿 2MiB 帧上限 → daemon 重启循环、在途 run 被杀**（P0-1）：影响「事件不丢/补读」与 G2/G3/G7。缓解：定义响应预算/分片；超限仅本请求失败、不重启。
2. **正常退出提前强杀 daemon → 未落盘事件丢失**（P0-2）：影响 T4/G5。缓解：统一退出预算 + drain 先于 checkpoint + 明确强杀点。

**P1**

1. 跨壳数据锁只覆盖一侧，计划允许 `busy_timeout` 降级（P1-1）→ 迁移窗口双开写库风险；需回退壳取锁或强制运维口径。
2. 启动顺序与 1.5s/2s 门禁冲突（P1-2）→ 门禁口径不可判定。
3. 错误码口径混用 + 未登记新码（P1-3/P1-4）→ G2 计数失真、UI 分支漏码。
4. `params` 包装未定（P1-5）→ 63 命令全局契约待裁定，M9-03 无法冻结。
5. 协议枚举/能力/通知未登记、通道名三处不一致（P1-6）→ G1 fixtures 不可固化、D7 未同步。
6. preload 白名单 vs `webUtils`（P1-7）→ 拖拽验收与安全断言二选一冲突。
7. 路径复核清单漏 `backup_create`/`export_diagnostics`（P1-8）→ 两个「写用户指定目录」命令成校验盲区。
8. 回退对象/可构建性未定义（P1-9）→ G5/G6 失败时回退路径不可执行。
9. 控制队列满即重启 daemon（P1-10）→ 一次 UI 卡顿杀全量在途 run。
10. 新壳级 UI 表面未入 UI-UX（P1-11）→ G4 壳级错误页无断言口径。
11. G7 含不可执行门禁项（T14/M1-08/ADR-001）（P1-12）→ 门禁无法签核。

**P2**

1. 决策缺逐条失效条件、风险表缺 owner（P2-1）。
2. 数字基线漂移（`bindings.ts` 1003 行 vs 923）（P2-2）。
3. 分组计数口径不一（§4.6 vs §16.1）（P2-3）。
4. `dialog.pick` 路由二义且 M9 无消费方（P2-4）。
5. P2 引入 P3/P4 承载但需求侧无登记（P2-5）。
6. universal 打包/嵌套签名/entitlements-Keychain 关系未决（P2-6）。
7. 覆盖率排除口径与 T15 关系未登记（P2-7）。
8. 锁的陈旧/迁移后归属未定义（P2-8）。
9. `export_diagnostics` 读 `shell.log` 的跨进程/脱敏/不可用场景（P2-9）。
10. debug 探针在 Electron 下的处置未定义（P2-10）。

### 8.4 新问题（v0.2 引入或未收口）

#### R-P0-1（P0，设计/验收）A4 阻断与迁移失败被当成「预 initialize 致命退出」，启动门流程不可实现

- **问题**：§4.2「预 `initialize` 失败（数据目录锁/**A4**/DB 打开/**迁移**）→ 写唯一首帧 error（`aether_code: data_dir_locked|startup_blocked|migration_failed|internal`）→ **按退出码表退出** → main 显示 **S-12**」；§4.3 退出码含 `21 数据目录检测失败`、`23 迁移失败`；M9-03 DoD5 更明确要求 fixture 覆盖「锁冲突/**A4**/DB/**迁移失败**」。这与三处契约冲突：
  1. §3.5-7：「启动门阻断（A4）时，`startup_get`/`startup_migrate` **仍可用**；业务命令返回 `startup_blocked`」——daemon 退出则两命令不可达；
  2. 设计附录 D **T13**：同步盘「拒绝启动（不进入主界面）；**仅「迁移」/「退出」两选项可用**」；
  3. UI-UX **S-12 动作 = 重试/退出/离线导出诊断**（**无迁移**）；S-01/S-01a 才承载迁移与 `blocked_error`。
  另：`startup_migrate` 发生在 `initialize` 之后，其失败本就不可能是「预 initialize 失败」；A4 检测在 §3.5-6 与设计 D2（line 283）中位于 `initialize` **之后**，与 §4.2 的归桶顺序也矛盾。
- **依据**：ADR-029 v0.2 §3.5-6/§3.5-7/§4.2/§4.3；`docs/P2-...v0.3` M9-03 DoD5；《设计文档》v1.26 附录 D T13、D2 启动序列（line 283）；UI-UX v0.15 S-01/S-01a/S-12。
- **风险**：按 ADR/DoD 实现即在 A4 阻断时杀掉 daemon → S-01 迁移入口失效（T13 门禁红）、`migration_failed` 无法重试（ADR-006 的 `pending_migration` 续跑语义失效）、G1/G4/G5 无法通过；「另一实例占用」与「同步盘阻断」被同一 S-12 呈现，用户无迁移路径。
- **建议**：把预初始化失败拆为三档并写死：
  ① **致命**（锁冲突、DB 打开/`quick_check` 失败、数据目录不可读）→ 首帧 error + 退出码（20/22/24）+ S-12；
  ② **可恢复阻断**（A4 同步盘命中、待迁移）→ daemon **继续运行**、`phase=blocked`、`startup_get`/`startup_migrate` 可用、S-01/S-01a；
  ③ 迁移失败 → 结构化 `migration_failed` + `pending_migration` 续跑，**不退出**。
  同步改 §4.3 退出码表（删除/限定 21、23）、M9-03 DoD5 fixture 分组、设计 D2 顺序说明；并在 `DaemonPhase` 与 `startup_get.phase` 之间给出映射（见 R-P2-1）。

#### R-P0-2（P0，设计/开发）`aether_code` 业务码命名空间与 ADR-018 A-7、现状实现、UI-UX §5 三处冲突

- **问题**：v0.2 §4.3/§16.2 规定「稳定业务码」是 `error.data.aether_code` 的登记值（示例 `"aether_code":"session_busy"`），并称「按 ADR-018 A-7 口径登记」。但：
  1. **ADR-018 A-7 原文**：业务拒绝「以 `invalid_value` + message 内的**稳定业务码前缀**表达」，「**实现任务不得把上述业务码登记为新错误码**；如未来需要前端按类型分支，须走 ADR-006 增行流程」；
  2. **现状实现**：`code="invalid_value"`、message 含 `（session_busy）`（`apps/desktop/src/m7_07_session_management.test.tsx` 即构造 `{code:"invalid_value", message:"…（session_busy）"}`；`session_backend.rs` 注释同）；
  3. **UI-UX v0.15 §5** 声明「逻辑判断一律按 `code`」，并把 `session_busy`/`storage_backpressure`/`memory_conflict` 列为「码/状态」行 → 与现状实现相悖，v0.2 等于把该表「转正」为线上契约（**修改已冻结的错误码语义**）；
  4. `data_dir_locked` 由 ADR-029 **自登记**，正是 A-7 所禁止的路径（且未走 ADR-006 附录 B）。
- **依据**：ADR-029 v0.2 §4.3/§16.2/§0（P1-3 行）；ADR-018 附录 A-7；ADR-006 附录 B 说明；UI-UX v0.15 §5；`apps/desktop/src/m7_07_session_management.test.tsx`；`crates/aether-tauri/src/session_backend.rs`。
- **风险**：错误契约在迁移中被**静默改变**（冻结项「错误码不变」被破坏）；G2 若按「Tauri/daemon 双跑」对照也无法发现（M9-02 后两侧共用 `aether-app::dispatch`，见 R-P1-1-d）；现有前端测试与会话/补选/改派路径的 message 解析需重写，`session_busy` 补选文案契约（ADR-028 v0.9）受影响。
- **建议**：二选一并写死：
  ① **保持现状语义**：`aether_code` 只取 32 枚举；业务码以新增稳定字段 `error.data.business_code`（+`kind`）承载，`error_codes.json` 收录两套但分字段；同步改 ADR-018 A-7 增行 + UI-UX §5 判定口径（`code` + `business_code`）；
  ② **提升为 aether_code**：则须改 ADR-018 A-7、ADR-006（业务码命名空间增行）、UI-UX §5、前端分支与测试，并明确「Tauri 基线对照」改用**发布版冻结 golden**（不能靠双跑自证）。

#### R-P1-1（P1，设计/验收）响应预算契约不完整，且 M9-04 DoD3 与 DoD4 / G2 自相矛盾

- **问题**：
  a. `next_cursor` 语义未定义（不透明 token？seq？offset？是否携带过滤条件？跨重启稳定性？与 `limit`/`offset` 同时出现时优先级？）——ADR-009 §9、ADR-023 A-4、设计 D7 均只说「返回 `has_more`/`next_cursor`」；
  b. **零推进风险**：单条 ≤1MiB、默认预算 1MiB，含信封/JSON 开销的单条即可能超预算 → 返回 0 条 + `has_more=true` + 游标不前进 → 客户端死循环；未规定「至少返回一条（允许短暂超预算）」；
  c. `messages_page` **默认分支同时返回 `events` 与 `messages` 两个数组**，单一 `has_more`/`next_cursor` 无法表达两流各自的截断；且 `messages` 被截断时无任何完整性信号（`complete` 只覆盖 events）；
  d. `audit_query` 已有 `has_more`（ADR-023 v0.3 的「多取一行」语义、offset 分页）与实现（`{rows,limit,offset,has_more}`），A-4 却写「响应增 `has_more`」；`next_cursor` 与 `offset` 形成**双分页通道**，未定义互斥/优先级；
  e. **门禁矛盾**：M9-04 DoD3 要求 `messages_page`/`audit_query` 与 Tauri 基线「结构化对照 **0 差异**」，DoD4 又要求这两条命令新增字段并截断 → 同任务内互斥；G2 行同时写「0 差异」与「预算分页」；
  f. **对照口径本身失效**：M9-02 之后 `aether-tauri` 也经 `aether-app::dispatch`，「双跑对照」两侧同源，无法发现契约漂移（含 R-P0-2）。
- **依据**：ADR-029 v0.2 §4.1/§4.7/D-029-4；ADR-009 §9；ADR-023 A-4 与 §2.1-3；《设计文档》D7 `messages_page` 行；`docs/P2-...v0.3` M9-04 DoD3/DoD4、M9-05 DoD5、G2；ADR-029 §3.3「aether-tauri …业务全部调用 aether-app」。
- **风险**：M9-04/M9-05 无法开工（契约不可判定）；UI 续页可能死循环、缺页或静默丢消息基线；G2 用同源自证通过但线上契约已变。
- **建议**：① 定义 `next_cursor` 为**不透明串**（服务端编码位置 + 过滤指纹，客户端不得解释；过滤条件每次重校验）；② 明确「最小推进 = 至少 1 条」与超预算允许上限（≤1.5MiB）；③ `messages_page` 分别给 `events_has_more`/`messages_has_more`（或限定预算仅作用于补读分支）；④ `audit_query` 明确 cursor 与 offset 互斥（建议仅保留其一）；⑤ 把 G2/M9-04 的「0 差异」改写为「与**发布版冻结 golden** 对照；`messages_page`/`audit_query` 预算字段列入**已登记差异**」；⑥ 冻结 M9-02 前的发布版 fixtures。

#### R-P1-2（P1，开发）`initialize` 把「目标值 2s」当硬超时，冷启动将误判致命

- **问题**：§3.5-5「`initialize` 握手（2s 超时）」，§3.5 指标「daemon 握手 ≤2s（目标）」，设计 D2 亦写「`initialize` 2s（不等待预热）」；2s 既是指标又是超时。冷启动/杀软扫描/迁移目录读取抖动会直接触发 S-12（致命页），而非重试。
- **依据**：ADR-029 v0.2 §3.5-5 与启动指标表；《设计文档》v1.26 D2（line 283）；P2 计划 M9-09 DoD1。
- **风险**：G1/G4 门禁抖动、用户侧「核心未能启动」误报；与「重试」动作语义冲突（超时后直接致命）。
- **建议**：拆为「目标 ≤2s（性能门禁）」与「超时 ≥10s（可靠性）」；超时后先重连/重试一次再降级到 S-12，并在指标中记录超时率。

#### R-P1-3（P1，开发）回退物时序缺口：M9-08 已放弃 HEAD Tauri，而冻结回退包到 M9-09 才存在

- **问题**：§9.3 与 M9-08 DoD3 规定「M9-08 起 HEAD 不再构建可用 Tauri UI；回退对象 = M9-09 重建并冻结的 Tauri 包」。但依赖图（P2 计划 §1.3/§1.2）中 M9-08 与 M9-09 为并行支路、M9-09 依赖 M9-07 且晚于 M9-08 的常用次序 → 存在「HEAD 不可回退 + 冻结包未就绪」窗口；且「从冻结 tag **加锁重建**」实为**带补丁的新构建**，与「冻结 tag 原样」不是同一物，需定义 rollback tag/branch 与哈希基线。
- **依据**：ADR-029 v0.2 §9.3、D-029-12；`docs/P2-...v0.3` M9-08 DoD3、M9-09 DoD5、M9-14 DoD1/DoD2、§1.2/§1.3。
- **风险**：G4/G5/G6 失败时无可执行回退物（回退门禁红）；「冻结包」与「冻结 tag」混用导致证据不可复核。
- **建议**：把「重建并冻结带锁 Tauri 回退包 + 哈希/日期」设为 **M9-08 的前置 DoD**（或把 M9-08 移后于 M9-09）；定义 `m9-rollback` tag（含取锁补丁）+ `git rev-parse`/安装包哈希/发布日期三元组入证据。

#### R-P1-4（P1，治理/契约登记）命令/错误码登记面未同步，生成物边界缺失

- **问题**：
  a. `error_codes.json` 被定为「TS union 与 G2 验收集合的唯一来源」，但 **AGENTS §2.8 生成物清单**（types/client/manifest）与 **§8 目录边界**未包含它，§5 自检清单仍写「tauri-specta 生成物/未修改 bindings」；ADR §7 生成物清单亦无 `error_codes.json`；§8.2 门禁只跑 `protocol check`，无 `error_codes.json` 的 diff/计数校验 → 可被手改且无 CI 拦截（违反 AGENTS §2.8 的 MUST）。
  b. **ADR-018**（命令/错误码登记所有者）未修订：A-1 `audit_query` 参数无 `max_bytes`；A-7 与 R-P0-2 冲突且未登记 `data_dir_locked`；A-8 未覆盖新增 UI 行。
  c. **ADR-006 附录 B** 未记录业务码命名空间决策（若按 R-P0-2 方案①，则需增行/增节）。
- **依据**：ADR-029 v0.2 §4.3/§7/§8.2；AGENTS §2.8/§5/§8；ADR-018 A-1/A-7/A-8；ADR-006 附录 B。
- **风险**：生成物可漂移（M9-04 的 `error_codes.json` 校验形同虚设）；登记面与实现面不一致，G2 证据不可审计。
- **建议**：AGENTS §2.8/§8/§5 增 `error_codes.json`（禁止手改 + CI diff）；§8.2 增 `pnpm verify:error-codes`（32 枚举 + N 业务码双计数）；ADR-018 升 v0.4 登记 `audit_query.max_bytes` 与业务码口径；ADR-006 增行/增节。

#### R-P1-5（P1，需求/开发）UI 侧新契约无规格：`data_dir_locked` 文案、预算续页 UX、S-12 承载

- **问题**：① UI-UX §5 无 `data_dir_locked` 行（ADR §3.5-4 要求「main 提示『另一个 Aether 实例正在使用数据目录』」，且迁移目标被锁时同一文案不适用）；② `messages_page`/`audit_query` 预算分页后的**续页 UX**（自动续读/「加载更多」/终止与取消/与 `readback_gap_too_large` 提示的关系）未在 UI-UX v0.15 登记，M9-08 仅写「分页续读」；③ S-12「主 UI 不加载时的壳级页面」但锚点/动作定义在 renderer 界面清单中，**由谁渲染**（独立最小窗口 vs 同一 renderer 的 pre-boot 页）未定义。
- **依据**：ADR-029 v0.2 §3.5-4/§4.1；UI-UX v0.15 §1.2/§1.2a/§5、S-12；P2 计划 M9-08 DoD5、M9-05 DoD5。

#### 9.3-2 裁定 2：业务码走 `error.data.business_code`（方案①）

**目标形状**：

```json
{"jsonrpc":"2.0","id":42,"error":{
  "code":-32000,
  "message":"会话正在运行，暂不能补选供应商/模型",
  "data":{"aether_code":"invalid_value","business_code":"session_busy","details":{...}}
}}
```

- `aether_code` ∈ **32 枚举**（`IpcErrorCode::as_str()`，不变）；`business_code` ∈ 稳定业务码（首项 `data_dir_locked`，沿用 `session_busy`/`session_paused`/`storage_backpressure`/`memory_conflict`/`permission_not_pending`）；**无细分需求时省略 `business_code`**。
- 前端判定顺序：`business_code`（若存在）→ `aether_code`；`message` 仍只用于展示。
- 兼容性：`business_code` 在 `data` 内为**增量字段**，旧客户端忽略；不改变 32 枚举、不改 `aether_code` 既有取值。

| 文件 | 条款 | 目标改法 |
|---|---|---|
| ADR-029 §4.3/§16.2 | 「业务码是 `aether_code` 的登记值」 | 改为 `business_code` 字段；`error_codes.json` 两数组（`ipc`/`business`）+ `kind`；`data_dir_locked` 首登记 |
| ADR-018 附录 A-7 | 「不得登记为新错误码」 | 增行：业务码经 `data.business_code` 承载，不入 32 枚举；新增业务码须在 A-7 表增行（含 `data_dir_locked`） |

#### 9.3-3 裁定 3：响应预算与 `next_cursor` 定稿

**建议直接采用以下口径（写入 ADR-009 §9 / ADR-023 A-4 / ADR-029 §4.1 / 设计 D7）**：

1. `max_bytes`：默认 **1MiB**、上限 **1.5MiB**、下限 **64KiB**；越界 → `out_of_range`；旧客户端省略按默认值。
2. **最小推进**：每页**至少返回 1 条**（即使略超预算）；总帧仍须 ≤2MiB，否则 `too_large`（提示减小 `limit`/`max_bytes`）。
3. `next_cursor`：**不透明** base64url，内容 `{v:1, stream, pos, filter_hash}`；客户端不得解析/构造；服务端每次重算并校验 `filter_hash`，不匹配 → `invalid_value`（防篡改与越权）。
4. `messages_page`：`next_cursor` **仅作用于 events 补读流**；另给 `messages_has_more`（首页 `messages` 截断时 true）；`complete`/`last_seq`/`readback_gap_too_large` 语义不变。
5. `audit_query`：`next_cursor` 与 `offset` **互斥**（同时传 → `invalid_value`）；`has_more` 语义 = 「还有更多行 **或** 被预算截断」；`limit` 仍 ≤500。
6. **对照口径**：M9-04 DoD3 的「0 差异」仅适用于未改契约的命令；`messages_page`/`audit_query` 的预算字段与截断行为列入**已登记差异**（基线见 §9.4-1），不得写成「0 差异」；G2 同步。
7. 文档落点：ADR-009 §9、ADR-023 A-4、ADR-029 §4.1/§4.7/D-029-4/§16.4、设计 D7、M9-04 DoD3/4、M9-05 DoD5、G2、UI-UX 续页 UX（见 9.3-1 的 UI 行）。

### 9.4 裁定引出的两个新约束（务必执行）

#### 9.4-1 **golden 基线必须在 M9-02 之前录制**（新的放行前置）

理由链：
1. 未发布过版本 ⇒ 没有「发布版行为」可对照；
2. 取消回退包 + M9-08 后 HEAD 不再构建 Tauri ⇒ 之后没有可运行的旧实现；
3. M9-02 抽层后 `aether-tauri` 与 `aetherd` 共用 `aether-app::dispatch` ⇒ 「双跑对照」两侧同源，**无法发现契约漂移**（R-P1-1-f）。

因此：**M9-01 证据中必须包含「迁移前 HEAD 基线包」**——63 命令的合法/非法/错误/分页边界 golden JSON（含 32 枚举与业务码现状、`messages_page`/`audit_query` 响应样本）、启动/关闭时序、事件样本、诊断输出；存放 `docs/M9-01-baseline/`，M9-04/M9-13 只允许**新增**基线，不得改期望值。未录制基线前不得开工 M9-02（因为抽层会改变对照物）。

#### 9.4-2 「数据可丢」不等于可以改冻结项

- `migrations/0001–0009` 仍**不可修改**（AGENTS §2.4/§8；设计附录 C 冻结）——「未发布」不是改迁移的理由。
- 63 命令、32 枚举、EventEnvelope 9 字段、设置键 9、附录 B 事件类型仍是 M9 验收基线；业务码只是**新增承载字段**（9.3-2），不是改枚举。
- 「数据可丢」仅适用于内测数据；发布前必须重新评估（建议在 ADR-029 §15 增一条「发布前重评数据兼容/回退策略」）。

### 11.4 剩余文档问题（本轮新发现）

#### R1（P1，设计/验收）`quick_check` 失败=致命退出，与设计 D3/D4「安全模式（只读 + 导出/备份）」及 ADR-007 只读呈现冲突

- **问题**：v0.3 把「DB 打开 + `quick_check`」放进预 `initialize` 致命检查（ADR §3.5-4），失败→首帧+退出码 22+S-12；但设计 v1.27 D3（line 309、325）规定 checksum 不符/库损坏 → 「**安全模式（只读打开 + 可读数据导出 + 从备份恢复）**」；D7 `health`（line 502）规定「启动失败（安全模式等）按 `persist_degraded` 只读呈现」。三者互斥：DB 可只读打开但完整性校验失败时，v0.3 直接杀进程，`persist_degraded`/S-08/导出备份路径全部不可达——数据损坏时唯一的自救路径被静默移除。
- **依据**：ADR-029 v0.3 §3.5-4、§4.3 退出码 22；设计 v1.27 D3、D7 `health`；ADR-007。
- **风险**：G5「旧库可开」与恢复演练口径不一致；库损坏只能丢数据重装；安全模式变死代码，后续启用又是一次契约变更。
- **建议（二选一，需裁定）**：① **保留安全模式**（推荐）：仅「DB 无法打开」（缺失/权限/加密头损坏）致命退出 22；「打开成功但 `quick_check` 失败」→ 只读 + `persist_degraded` + S-08 + 导出/备份入口；② **明确取消安全模式**：ADR §0.1 记范围收缩 + 改设计 D3 两处/D7 `health`/ADR-007 增注，并声明内测期只靠备份与诊断导出。选①时 `db_open_failed` 仅指「不可打开」，M9-03/G1 的 DB fixture 拆「不可打开」「校验失败」两类。

#### R2（P2）「63/63」与「61/63 可达」同格并存，参数矩阵覆盖被收窄

- **问题**：ADR §10 G2 写「63/63 路由/契约、**61/63 可达**」；P2 M9-04 DoD2 把参数矩阵限定为「M9 可达命令（61/63）」。daemon 仍 `dispatch` 全部 63，「可达」实际只指 UI 暴露；两条命令的校验矩阵因此不再验证，仍属 63 冻结契约。
- **依据**：ADR §10 G2；P2 M9-04 DoD1/DoD2；M9-01 DoD9（基线按 63 录）。
- **建议**：分开表述与取证——「**命令合同 63/63 覆盖（RPC 层矩阵/golden）**；**UI 暴露 61/63**」；M9-04 DoD2 矩阵恢复 63 条。

#### R3（P2，治理）ADR-006/009/023 增补未升版；ADR-009/023 缺 `filter_hash` 校验句

- **问题**：ADR-010/018/028 已升版并记变更行，同批 ADR-006（v0.8）、ADR-009（v0.2）、ADR-023（v0.3）**未升版、无变更行**——与 §9.3-6 确立的「编辑性也要版本行」同规遗漏。另 ADR-009 §9/ADR-023 A-4 只写 cursor 结构，未写「服务端每次重算并校验 `filter_hash`，不匹配→`invalid_value`」（ADR-029 §4.1 有），契约所有者文档不完整。
- **依据**：ADR-006 头部/§8；ADR-009 头部/变更记录/§9；ADR-023 头部/变更记录/A-4；ADR-029 §4.1。
- **建议**：ADR-006→v0.9、ADR-009→v0.3、ADR-023→v0.4 各补变更行；两处补 `filter_hash` 句。

#### R4（P2，可执行性）M9-01 要求 `verify:error-codes` 通过，但 `business_code` 常量到 M9-02/M9-03 才存在；G0 条件未列该脚本

- **问题**：M9-01 DoD10 要求「`verify:version`/`verify:error-codes` 通过」，而 M9-01「不写业务代码」，`business_code` 字段/常量当前不存在（现状是 message 前缀）；生成器「business 集合 = 代码常量集合」在 M9-01 不可能成立。G0 通过条件也只列「统计脚本/基线」。
- **依据**：P2 M9-01 描述/DoD4/DoD10；ADR §4.3；G0 行。
- **建议**：拆分——M9-01 = 生成器骨架 + `error_codes.json`（ipc 32）+ schema/diff/去重/kind；**M9-03 起**启用 business 集合校验；G0 补「生成器/脚本存在且 ipc=32 通过」。

#### R7（P2）`startup_pick_target` 的「无启动 UI 入口」易被误读为「无任何 UI 入口」

### 13.2 本轮唯一 P1（R10）安全模式的「从备份恢复」路径二选一未定

- **问题**：R1 承诺「`quick_check` 失败 → 只读安全模式（可读数据导出 + **从备份恢复**）」（ADR §3.5-6），但文档三处未配套：
  1. 设计 D4「降级期语义」只列「读查询、诊断导出、**备份/导出**保持可用」（line 371），**未列 `backup_restore`**；D4 同时是「拒绝新写入与新 run」的强制口径，实现者按字面会把 restore 当写操作拒绝；
  2. D13 恢复流程要求「停写 → 关闭连接 → 现场保护 → 就位 → **重启核心**」（line 671–679）；daemon 架构下等价于「重启 daemon」，但 ADR/P2 未说明 safe mode 下 `backup_restore` 的执行者、是否复用 §3.6 关闭序列、是否由 main 重启 daemon；
  3. UI-UX S-08 动作只有「重启应用/导出诊断」（line 490），无「恢复备份」入口；S-08 又称「读/备份/导出可用」——库已损坏时 `VACUUM INTO` 备份是否可执行也未区分。
- **依据**：ADR-029 v0.4 §3.5-6；设计 v1.28 D4（line 371）、D13（line 671–679）；UI-UX v0.17 S-08（line 490）、S-06；`backup_restore`（ADR-006/ADR-018）。
- **风险**：G5 数据演练「quick_check 失败 → 从备份恢复」可能因降级门禁不可执行；用户唯一自救路径不可达；R1 的修复在验收层不完整。
- **建议（二选一，均为一句话级，二选一后即关闭）**：
  - **A（推荐）**：设计 D4 增「维护操作例外：`backup_restore` 在 `persist_degraded` 下允许——先停写/关连接，恢复后由 main 重启 daemon（复用 §3.6 关闭序列）」，不算新写入；UI-UX S-08 增「恢复备份」入口（指向 S-06，`data-mode="restore"`），S-08 的「备份可用」改「导出可读数据 / 恢复备份」；P2 M9-13 DoD4、G5 增该断言；
  - **B（产品接受）**：明确「安全模式不提供恢复入口，仅导出可读数据 + 手工替换库文件」，同步删除 ADR §3.5-6 的「从备份恢复」承诺、S-08 的「备份」字样，并在 §2.1/§11 记风险接受人。
